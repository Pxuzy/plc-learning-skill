# 源码归档稿（Source Archive）

用户分消息贴源码且仅要原样 Markdown 时，交付**源码资料**：不讲解、不写功能定位、不加注释、不补逻辑、不评价。

## 适用判定

- 用户要求保存、排版或归档，且没有要求讲解。
- 用户要求解释或修改时，回到相应主流程，不用归档代替讲解。

## 流程

1. **清点输入**：按用户提供的顺序记录片段编号、起止位置、完整或截断状态。预期片段集合来自本次输入清单，不写死数量；比较已收到与预期集合，缺项明确列出。
2. **原样保存**：源码及原作者注释逐字符保真，不重排、不补条件或结束语句、不修疑似笔误。只有上下文明确证明是同一片段的连续消息时才拼接，否则分开保存并注明关系待确认。
3. **标注缺口**：把缺失位置与缺少的资料写在对应片段旁，整理者拟定的标题显式标注。不得用旧讲义、示例或不同版本资料填补源码。
4. **核对声明**：分别统计各类 VAR 声明块；变量名、类型、方向、初值和顺序照原文保存。声明缺失时不根据命名补写。
5. **落盘后比对**：重新读取交付文件，提取每个源码围栏，与输入清单中的原始片段逐一比较；同时检查围栏闭合、目录锚点、片段集合和文件哈希。验证记录的文件名依本次交付约定，不使用工程特有命名。
6. **保护原件**：默认新增文件；更新已存在的归档前先确认目标，保留原版与变更证据。
7. **建立索引**：用相对链接记录用途、来源、版本与缺口；后续分析引用归档标识和片段编号，便于回查。

## 版式

- 头部记录资料名、来源、归档日期、原文范围与未读取的外部资料。
- 声明区、源码区和缺件说明分开；使用稳定编号和目录锚点，不绑定特定工程的章节名称或数量。
- ST 使用独立、闭合的 `iecst` 围栏；声明表与标题之间留空行。
- 原始消息仅在用户授权且确有回查需要时保存到交付区，执行脱敏和访问控制；不进入技能仓库或公共样例。

## 常见失败

- 把讲解稿中的改写实现当成原始源码，导致后续失去可靠依据。
- 未检查片段集合或截断边界，交付时静默缺失内容。
- 写完文件未读回，围栏错误或意外改码没有被发现。
- 用省略语代替缺失源码，让读者误以为归档完整。
