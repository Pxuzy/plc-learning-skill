# 源码归档稿（Source Archive）

用户分消息贴源码且仅要原样 Markdown 时，交付**源码资料**：不讲解、不写功能定位、不加注释、不补逻辑、不评价。

## 适用判定

- 用户说“保存为 md / 存成文件 / 以后我要引用这些代码 / 格式注意一下”，且没有要求讲解。
- 只要用户要讲解或改程序，回到主流程（HBK / 修改先确认），不要退回本流程。

## 流程

1. **先盘点消息，再动手**：按消息 id 逐条读回原文，列出已收到的节号与每节最后一行；`re.split(r'(?m)^### 节(\d+)：([^\n]*)\n', joined)` 切节，断言 `set(sections) == set(range(1, 11))`，缺节直接暴露而不是静默丢内容。
2. **代码只用原文**：跨消息截断节去掉节首 `iecst` 围栏后接前节尾；围栏内逐字符保真，不重排、不补 `THEN`/`END_IF`、不改疑似笔误。
3. **缺口写在节上，不用旧稿补**：半节标题下写 `> 缺口：…停在哪个判断，其后未收到`；自拟标题标“本标题为整理标题”。早前手册/讲义改写过代码，不可补源；XML 标识不同视为不同版本，正文注明“两者是否同版本未确认”。
4. **变量表按块计数校验**：逐 `VAR`/`VAR_INPUT`/`VAR_OUTPUT`/`VAR_IN_OUT`/`VAR_EXTERNAL` 统计数据行，`assert counts == expected` 对预期字典，入口汇总总数；名/类型/序号保真。
5. **对账后才称完成**（核心步骤）：写出文件后重新从磁盘读回，用 `re.findall(r'(?ms)^```iecst\n(.*?)\n```$', saved)` 取出全部代码块，逐个 `assert code == sections[n]`；再断言围栏数为 2 倍块数、目录内链锚点都存在、`sha256` 写入 `归档校验.json`。
6. **不覆盖既有归档**：`assert not path.exists()` 再写；要更新就换文件名或先让用户确认。
7. **归档索引**：目录 `README.md` 用相对链接说明缺口/用途；同份 `.md` 导入资料索引（见 knowledge-evidence-index），可按功能块名或中文功能名检索。

## 版式

- 头部元信息写 `工程：` 与 `讲解深度：归档（不讲解）`，源码出处写成“用户原文标注的 XML 名称”，并声明“未读取 XML 原件”。
- `## 一、变量定义` / `## 二、ST代码`，每节 `<a id="section-N"></a>` + `### 节N：标题` + `iecst` 围栏；`### 变量块` 与表格之间留空行。
- 末节 `## 三、资料缺口与后续使用`：逐条列缺什么、下次该向用户要哪段。
- 保留原始聊天到同目录 `原始会话片段.json`；tool 类消息只摘用户回复另列，不整段堆聊天。

## 常见失败

- 把讲解手册的改写代码当成源码写进归档 → 归档失去证据价值，后续分析全建立在错误来源上。
- 拼节时不校验节号集合 → 缺节被静默吞掉，对账时才发现，返工重写。
- 只做 `path.write_text` 就宣布完成 → 实际围栏错位或代码被顺手格式化，必须从磁盘读回比对。
- 用“其余略”或“同上”代替未收到的源码 → 用户以为是完整稿，后面据此排故会误判。
