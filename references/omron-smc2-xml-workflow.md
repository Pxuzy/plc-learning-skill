# 欧姆龙 SMC2 XML 分析工作流

**状态：方法参考，不表示已验证所有 Omron 工程或版本的解析支持。** 仅在已确认品牌为 Omron、产品线为 NJ/NX、来源为 Sysmac Studio SMC2，且本次容器/字段结构适用时加载。品牌相同、后缀相同或已经解包都不够；控制器与软件版本未提供时记录未知，按当前样本核对，不能推广为全版本支持。其它品牌/格式回到[通用工程读取](workflows/read-project.md)和[厂商经验入口](vendors/README.md)。

## 一、条件适用的读取顺序

```text
核实来源、版本线索和真实容器结构
→ 安全清点归档（或清点用户已解包目录，注明未核对原归档）
→ 需要时用可用工具受控解包到独立副本
→ 检查当前样本中的 .oem / 其它工程描述及真实 schema
→ 若 .oem 确实承载对象层级与引用，据此恢复原生工程树
→ 按真实引用映射 .xml / .json / .st 或样本实际的代码与配置对象
→ 回读声明、程序体、调用和变量，核实映射与缺口
→ 回到原定导航/局部讲解/完整范围路线
```

`.oem` 是本方法预期检查的描述文件，不是所有版本必有的固定 schema。未发现它、它不含层级引用、或字段与经验冲突时，不凭文件名拼树；记录差异，检查实际描述/引用，必要时索取最小工程树或目标导出。不臆造专用解析器，不把描述字段当 ST 程序体。

## 二、归档清点器的真实能力

有 Python 和真实归档时，可在技能根目录执行：

```sh
python3 -B scripts/inspect_smc2_archive.py <工程.smc2> --json
```

该脚本检查 ZIP 成员、扩展名数量及 XML/JSON 的可解析状态；**不解包、不重建工程树、不提取程序体、不推断对象调用关系**。已有合成容器回归，不证明真实工程语义或厂商版本支持。无脚本环境可使用已获准的工具/用户侧输出，但要准确区分亲自执行与接收他人结果；工具缺失不阻断已有可读代码的讲解。

预检拒绝重复成员、盘符/越界名与编码 DTD。默认预算为 5000 成员、总解压声明量 512 MiB、单成员 256 MiB；元数据每文件最多解析 8 MiB，可用 `--max-metadata-bytes` 显式调整，其他参数查 `--help`。读取结果的 `metadata.complete` 和逐文件状态；`incomplete` 不能称完整解析，`xml-ok` 只证明 XML 可解析，不证明是有效工程、含源码或映射完整。清点通过后仍须由受控解包工具校验实际写出路径、大小和内容；不修改原工程。

## 三、核对真实结构并建立映射

按本次范围记录：

- 来源名、清点/解包方法及实际结果位置；文件总数和各扩展名数量（仅在确实完整清点时给总数）。
- 工程软件/版本、控制器型号及证据；未提供就写未知。
- `.oem` 或实际描述文件的编码、根节点、命名空间/版本、层级与引用字段；给 XML 路径或对象 ID。
- 每个目标节点到源码、声明、类型、变量表和配置的映射依据；导出/副本行号与原件坐标分开。
- 程序体是否真实可读，是否混有 ST、Ladder 或其它语言；不把整个工程统一称为 ST。
- 断链、重复/孤立对象、同名实例歧义、空节点、保护/加密、截断与部分映射。

可能看到任务、程序单元、段或网络，但只保留当前工程实际表达的层级，不造 `Task → POU → Section` 节点。XML/OEM 的文件或节点排列不证明调用顺序；任务登录、实例调用绑定和代码内部顺序分开取证。

每条关系记录来源对象、目标对象、调用/引用位置、可见输入输出、时间/顺序证据及结论强度。区分定义与实例、工程组织与运行调度、直接 ST 文本与 XML 结构推断、已确认工程事实与现场用途推断。详见[定位与追踪](locating-and-tracing.md)。

## 四、FB/MFB 与 ST 的按需阅读

这部分只是取证清单，不另定讲解格式：

- FB/MFB：定义、库/版本与实例归属；各输入、输出、IN_OUT 和实例变量的声明；调用点与实参绑定；输出消费者；可见状态、异常和复位。Execute/Busy/Done/Error 等指令语义须查匹配平台/库资料，不能仅按名字套通用语义。
- ST：先把握所选对象职责和完整父结构，再分解子块；按源代码顺序分析条件、写入/不写、后写覆盖及上下游。跨扫描结论必须具备实际调度/调用证据或明确条件假设。
- 受保护或仅接口可见的块，说明可见接口/调用与未知内部，不猜实现，不绕过保护。
