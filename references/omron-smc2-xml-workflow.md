# 欧姆龙 SMC2 XML 分析工作流

适用于 AI/工具解析欧姆龙 `.smc2` 的文件。按归档处理：**先解压，再以 `.oem` 重建工程树，最后映射并分析 `.xml/.json/.st` 文件**。结构以当前样本为准，不预设 schema。

## 一、总流程

```text
.smc2 归档
→ 调用用户侧可用工具解压到工作目录
→ 清点全部解压文件及扩展名（.oem/.xml/.json/.st 等）
→ 读取 .oem 工程树描述文件并恢复层级
→ Tasks → Program Units / POU → Sections → 对应代码/配置文件
→ 依据工程树引用映射具体 .xml/.json/.st 文件
→ 检查映射完整性和重复/孤立文件
→ 清点调用、变量、段/网络并建立交互图
→ 生成项目索引与学习对象清单
→ 用户选择对象，每个对象单独生成一份 .md
→ 内容审查与适用校验
→ 交付项目索引 + 对应对象文档
```

消费用户 AI/工具的真实解包与 `.oem` 解析输出，不谎称自行执行；记录输出目录、清单、工程树证据。图示 69 文件仅示例，非固定数量。

XML 事实不自动证明结论；字段/层级/调用/ST/地址保留原标识，报告记 XML 路径或对象 ID。

## 二、先确认 XML 是否可用

归档预检先用 `inspect_smc2_archive.py`，拒绝重复成员、盘符/越界名与编码 DTD。默认预算为 5000 成员、总解压声明量 512 MiB、单成员 256 MiB；元数据每文件只解析 8 MiB，可用 `--max-metadata-bytes` 显式提高。读取 JSON 的 `metadata.complete` 与逐文件状态；`incomplete` 只代表清点完成、元数据未全解析，不能据此宣称工程树完整。预算参数详见 `--help`。

首轮必须检查并写入 `00-项目索引.md`：

- `.smc2` 来源名、解包工具/结果位置、实际文件总数与各扩展名数量；
- `.oem` 文件名、编码、根节点、命名空间/版本（如有）及工程树解析结果；
- 工程树每个节点到实际 `.xml/.json/.st` 文件的映射依据；
- XML 文件名、读取日期、编码、根节点和命名空间；
- 工程版本、控制器型号、任务数量、程序单元数量；
- XML 是否包含完整程序体、变量表、段/网络、调用关系和注释；
- 是否存在空节点、加密节点、受保护块、截断文本或重复对象 ID；
- XML 与用户描述的工程对象是否一致。

先查 `.oem`/源码真实 schema/字段，不凭字段名套通用解析。字段缺失/语义冲突先确认；不凭对象名猜归属，不凭归档/XML 排列猜执行顺序。

## 三、对象层级与交互

工程树索引依 `.oem` 实际表达；样本层级不同保留源结构、注明差异，不造节点：

```text
工程
├── 控制器
├── Tasks / 任务
│   └── Program Units / POU
│       └── Sections / 段（如 SR_Mapping、SR_Auto、SR_CyclicCall）
│           └── 对应的 .xml / .json / .st 文件
├── 变量与地址
├── 调用点与被调用对象
└── HMI / 通讯 / 参数 / 报警 / 安全相关对象
```

每个交互至少记录：来源对象、目标对象、触发条件或调用位置、输入参数、输出参数/状态、执行时机、证据等级、XML 路径或 ID。

必须区分：

- FB/MFB 的定义文档与实例调用文档；
- 程序单元的内部逻辑与任务中的登录/调用顺序；
- ST 代码文本与由 XML 结构推断出的流程关系；
- 已确认的 XML 事实与待用户确认的现场含义。

## 四、学习对象与 Markdown 文件拆分

每个独立对象单独编号生成 `.md`，不混成长文：

```text
00-项目索引.md
01-整机或主程序框架.md
02-任务与程序调用链.md
10-ST-<程序单元名>-整体框架.md
11-ST-<程序单元名>-大框架-01-<主题>.md
12-ST-<程序单元名>-大框架-02-<主题>.md
20-MFB-<功能块名>-功能与接口.md
21-MFB-<功能块名>-内部逻辑.md
30-交互-<来源>-<目标>.md
90-待确认与审计.md
```

拆分规则：

- 用户要整体框架：生成主程序/程序单元整体框架文档，不把 MFB 细节塞进框架文档；引用对应 MFB 文档。
- 用户要 MFB/FB：独立讲接口、实例调用点、输入输出、状态、时序、报警、内部 ST/LD、外部影响；受保护只讲可见接口/调用。
- 用户要 ST：先整体框架，再按大框架分文档/批次，最后逐段精讲，回链大小框架。
- 用户要段/网络：仅该范围独立文档，开头列所属单元/大小框架、前置条件、后续影响。
- 未指定对象：仅先给项目索引/可选对象，不擅自展开全部对象。

## 五、ST 特殊要求

有 ST 的程序单元必须按以下顺序：

```text
ST 总框架
→ 大框架：完整职责/路径/接口/状态/异常
→ 小框架：子流程或网络组
→ 逐段精讲：源代码顺序与 XML 证据
```

不对 XML 标题各写两句即跳走；当前大框架未完，下文档/批次继续，并在台账登记。

逐段精讲必须包含：原始 ST、XML 对象路径/ID、用途、有效行内注释和块级条件与结果、变量变化、扫描周期影响、输出归属、异常/复位、容易误解、与上/下游对象的关系。

## 六、MFB/FB 单独精讲

MFB/FB 文档必须回答：

1. 该块的定义、版本、库来源或工程归属；
2. 每个输入、输出、IN_OUT、实例变量的实际含义和证据；
3. 所有调用点、调用顺序、传入参数、输出使用者；
4. Execute/Enable、Busy/Active、Done、Error、ErrorID 等执行语义；
5. 状态变化、完成条件、异常和复位条件；
6. 与任务周期、前后工位、通讯或运动对象的交互；
7. 内部 ST/LD 可读代码的分层讲解和全量覆盖状态。

仅接口、缺本体或 XML 标保护，标题/结论标 `受保护/部分可见`，不凭 MFB 名猜内部。

## 七、用户选择与确认规则

用户的自然语言决定对象和深度：

- “看整体” → 主程序/程序单元整体框架；
- “讲这个 ST” → ST 总框架 + 大框架 + 小框架 + 逐段精讲；
- “讲这个 MFB/FB” → MFB 独立文档；
- “讲这段” → 指定范围独立文档；
- “讲它们怎么交互” → 交互文档 + 双向引用。

仅改变范围的关键歧义需确认：同名实例归属、缺调用者、程序/任务顺序冲突、“功能块”指定义还是实例。文件编号、章序、默认代码深度自行决定。

## 八、交付

最终交付：

- `00-项目索引.md`：事实清单、对象地图、学习顺序、文件索引、未覆盖与待确认；
- 用户选择对象对应的一个或多个独立 `.md`；
- 需要时提供交互关系文档和完整性审计文档。

各文件统一项目术语/对象 ID/XML 路径/版本；未确认结论集中 `90-待确认与审计.md`，不藏正文。
