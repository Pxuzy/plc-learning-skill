# 用外部模型试跑本技能（隔离试跑台）

目的：验证「只有技能、没有其它工具」时，某个模型是否能凭一句简单提示按模板出稿。检查的是**技能可用性**，不是模型通用能力。

## 试跑台搭建（每次一个独立目录）

1. `root = scratch/plc-skill-trial-<时间戳>`，里面建 `hermes-home/`，把技能**软链**进 `hermes-home/skills/`（`ln -s <技能目录> ...`），不要复制，保证测的是当前工作树版本。
2. 试跑所需的提供方凭据从当前进程环境或凭据管理器注入，不写入仓库、技能目录或试跑工作区；`hermes-home/config.yaml` 设 `model.provider/default`、`providers.<name>`、`agent.max_turns`、`agent.run_budget_seconds`、`memory.*_enabled: false`、`plugins/mcp_servers` 置空。
3. 提示词只写一句自然语言 + 源码正文；不给文件路径、不列步骤、不提示模板编号。源码前加一行归档边界（哪几节 `partial`），否则模型会把缺口当已补全。
4. 调用：

```
HERMES_HOME=<root>/hermes-home hermes chat --provider <p> --model <m> \
  --skills plc-learning-skill --toolsets skills \
  --query-file prompt.txt --oneshot --format stream-json --max-turns 100
```

`--toolsets skills` 是「只准调用技能」的实现方式。不传 `--run-budget`（该 CLI 参数不被接受，进程以 exit 2 结束）；回合上限用 `--max-turns`，时长用 config 的 `agent.run_budget_seconds`。

## 必须核对的四项

| 项目 | 怎么查 | 通过标准 |
|---|---|---|
| 真的调了指定模型 | `events.jsonl` 第一行 `system/init` 的 `model` | 与请求一致 |
| 真的只用技能 | 统计 `type=='tool_use'` 的 `name` 集合 | 只有 `skill_view`，无 `terminal`/`file`/`web` |
| 技能确实被读 | 同一统计里的 `file_path` | 至少读到模板、讲解流程、证据规则 |
| 出稿是否合格 | `validate_handbook.py` + 源码剥离 `// AI:` 后逐字符比对 | 结构与源码保真各自计数，不合并 |

模型在正文里自称「校验已执行」「10 节全覆盖」**不是证据**：只能用上面的脚本结果。自述通过而围栏吸附时，源码块会被提取为 0 行，必须按上表逐项实测后才可报告通过。

## 小模型出稿的典型塌陷

- **围栏与源码粘连**：输出 `` ```st(*FB... ``（语言标签后没有换行），提取器拿不到块，校验报 `section-missing` / 源码覆盖率 0。交付前逐块检查 `` ``` `` 后紧跟换行。
- **标题名漂移**：把「批判性审查」「验证状态」改成自造小节名，模板校验缺项。段落内容可以自己写，栏目标题必须照模板。
- **把「无写文件工具」写进正文**：这是会话限制，不是手册内容，需删。

判定口径：技能可用 = 读到了技能并大体按主线 + 分段组织；模板合格 = 校验器零错且源码保真。两者分别报，不能因为「讲得像样」就报模板通过。

## 生成器改造的真实样本验收（模板/分批/续接改完后）

改造验收分三层，逐层分开报，不许合并成一个「通过」：

1. **离线回归**：单元测试 + foundation/格式检查 + `git diff --check`。只证明代码没坏。
2. **合成夹具**：几十个单元的长稿只证明**拼接、编号、断点恢复**；它用的是本地模拟传输，**不证明模型能按模板生成**，也不证明长上下文不退化。报告里必须写明这一层的边界。
3. **真实模型样本**：同一输入重复跑，每次落盘 `request.json`、`process-N.log`、成品与 sha256。核对四件事——请求里只有目标技能与正确工具集；模板正文确实进了提示词（不是只存在于模板文件里）；拒收/重试计数（截断、JSON 解析失败重试是正常路径，记 `rejected` 而不是判失败）；成品通过格式与源码保真校验。

样本量少（个位数）时只能报「N 次均通过，稳定性待更多样本」，不能写「生成已稳定」。合成层与真实层结论合并陈述即构成夸大。

**每层都要有真实请求证据，不能只看实现报告。** 子代理回报「已实现、测试通过」只证明它自己跑过的东西；拿到报告后自己重跑回归、自己抽查成品，并核对工作树改动是否只在白名单路径内（复算基线 sha256、`HEAD` 与暂存区不变）。

## 批量字段生成：截断先查输出预算

长批量按单元生成结构化字段（JSON）时，若响应成批被截断在半个对象里，先怀疑**输出额度被隐藏推理吃掉**，不要先改模板或缩小单元：请求里关掉可选推理（`reasoning: {enabled:false}` 一类）并抬高 `max_output_tokens`，再看是否恢复。判定证据是响应体的 `usage`／`finish_reason`——`length` 且正文未闭合即为预算问题。

- 截断响应一律拒收，按单元重试，**不要把半截 JSON 合入成品**；已通过的单元保留，不整体重跑。
- 原始失败响应与重试计数落盘（`rejected` 计数单列），报告里区分「已完成尝试数」与「被接收单元数」，两者不等是正常的。
- 修改请求参数前后各留一份真实请求/响应样本，否则无法说明恢复是参数起效还是偶然。

## 空结果与退出码

服务端返回「无可用账号」「限流」一类错误时，包装脚本仍可能 exit 0、日志一片正常。判定一轮审查/生成是否成立，只认落盘记录：条数达到预期、键集对得上（每个已生成的注释行都有对应审查记录）、进度文件 `completed == total`。不成立就换通道或如实报「本轮无有效结果」，不把空结果计入通过，也不把换通道后的结果与前一轮混算成一个验收项。

## 门禁本身要被反例测试

校验器通过率高不等于门禁有效。新增或修改检查后，至少构造这几类反例确认会被拒收：把缺失内容藏进 HTML 注释（`<!-- -->`）后仍被当作已展示、正文只剩标点、源码块被围栏吸附成 0 行、栏目名自造、把表头行插进变量数据行。同时确认没有误伤：源码围栏内的 HTML 字面字符串是合法源码，不能被「隐藏内容」规则一起拒。
