# 生成器构建长手册与校验收敛 🔨

讲解大型源码（几十个模块、上千行）时，手写 Markdown 必然破坏源码保真并在校验器上反复返工。用脚本切片生成，逐字复制、只追加注释，再让校验器逐轮收敛。

## 为什么用生成器而不是手抄

`check_code_integrity` 比对的是去掉追加注释后的源字符。手抄会无意识改空格、改缩进、合并续行，判“改写源码”后要逐行回查。生成器只做三件事：按源行号取行、在行尾追加注释、拼段标题，源码永远来自源文件。

## 分段切点三条硬约束

1. **不拆语法结构**：段边界不落在 `IF…END_IF`、`FOR…END_FOR`、`CASE…END_CASE` 中间；一个段可以包含多个完整结构，但不能只含其中一半。
2. **切点不得落进 `(* … *)` 块注释**。起点在注释内，校验器会把注释里的旧代码当成可执行行报“缺少行内注释”；终点在注释内，报“块注释未闭合，不能可靠划分注释”。先按行算注释深度，把起点回退到 `(*` 所在行、把终点推进到 `*)` 所在行，再输出。
3. **扩段尾判的是下一行**：判断“这一行之后是否仍在注释里”要用 `depth[e+1] > 0`，不能用 `depth[e]`——当前行自身就是 `(*` 起始行时 `depth[e]==0`，会漏判并切在注释中间。

段长按逻辑取（约 3～8 行），长 IF/CASE 整段保留、段内按条件分组讲，不为凑短复制代码。

## 按功能分块：以 `join` 断言保真

用户要求“代码适当分块、按功能切”时，切的是**呈现**，不改源码内容。生成器里必须带一条硬断言，而不是事后统计行数：

```python
chunks = split_functional(body)
assert ''.join(chunks) == body, item['number']
```

- **不要对每块 `rstrip('\n')`**。围栏按 `'```st', chunk, '```'` 拼时，块自己的结尾换行就是块间分隔；strip 掉以后每个非末块少一个字符，总长差恰好等于块数（10 块时序言从 11418 变 11420）。看到只有多块节差 1～3 个字符，先查这一处，别当成源文件变了。
- **从成品回读校验时同样不能 strip**：`re.findall(r'```st\n(.*?)\n```', part, re.S)` 已经保证块内含其结尾换行，再补一次 `.rstrip()` 就重现同一个丢字，而且报错会指向“源码缺字符”而不是生成器。
- 校验粒度是**按模块区间拼回后与对应源节逐字比较**，不比总字符数或总行数——总长相等仍可能整体错位，只有逐节 `join` 相等才算保真。
- 功能分块与“不拆语法结构”并存：块边界仍落在完整闭合结构或语义单元上，不切断表达式、单条赋值和原注释。
- 版式契约（目录置前、代码集中到单一章节、`M01…` 连续编号、每模块 ≥2 个功能源码块）同时落成 `evals/` 单测与可直接跑的 CLI 检查器，两者共用同一套正则；只写在文档规则里，下一次改版会静默退回旧版式。

## 复用既有逐行注释映射出稿

同一对象反复改版模板时，逐行注释已经做过一轮，重建手工再写必然漂移。做法是把注释存成数据（`{节号, line_count, chunks:[{start,end,title,explanation}], annotations:{行号: 尾注}, exceptions:[{start,end,reason}]}`），生成器只负责取值拼装。

- **切块以映射为准，不从旧稿继承**。源码映射细分后，旧稿切块边界可能失效；须按当前映射重新核对，使正文与注释位置一致。生成时断言 `chunk.start` 连续等于游标、游标走完等于 `len(lines)+1`，断一处就报节号与块号。
- **断言映射与源码同长**：`entry['line_count'] == len(raw)`，并按节把 `annotations` 的键校验为 1..N 范围。行数变了说明源换版，整张映射作废重做，不要按偏移硬套。
- **注释只加在可执行行**：追加前断言 `line.strip()` 非空且原行不含 ` // AI: `，避免重复追加或往空行、纯注释行上贴尾注。
- **每块带 `<!-- src: archive-section-N; lines:a-b -->`**，校验器据此把成品围栏与归档节对位，报错能直接指到块。

## 逐行注释的例外覆盖审计

只统计“有 N 条注释”证明不了覆盖：漏掉的可能是整块条件行。审计要双向对齐——

```python
annotated = set(entry['annotations'])
excepted = {n for x in entry['exceptions'] for n in range(x['start'], x['end']+1)}
uncovered = [n for n,l in enumerate(raw,1)
             if l.strip() and n not in annotated and n not in excepted]
invalid  = [n for n in annotated if not raw[n-1].strip()
            or raw[n-1].lstrip().startswith(('//','(*','*','*)'))]
assert not uncovered and not invalid
```

- `uncovered` 非空说明有可执行行既没讲也没登记例外，必须补讲或补例外理由；`invalid` 非空说明尾注贴在空行或注释行上。
- 例外按连续区间登记并写理由（空行、纯注释、块注释整体），不按单行散列；区间要能拼成一句读得懂的“哪几行、为什么”。
- 交付数字分别报：节数、源码行数、块数、尾注数、例外组数，外加“剥离尾注后逐节与归档逐字符一致”。总数相等不等于逐节相等，逐节比才是保真证据。

## 注释去重与作者原注释

- 行内注释以简短业务含义和必要触发条件为主，不加“教学补充”前缀；机制、覆盖顺序与推演放围栏外。检查器独立检查最后一段以 ` // ` 分隔的新增说明，同时兼容历史前缀。
- 原作者恰当的重复注释保留，逐处核对当前作用；不同业务才补具体区别。不要靠行号、换同义词或拆块规避重复诊断，无法消除的原文诊断如实登记。
- 完整、非嵌套、单简单赋值的 `IF … THEN x := 1; END_IF;` 可共用一句触发条件与业务说明；真正多动作仍用 `单元1：… | 单元2：…` 分项。具体覆盖边界以 `references/comment-quality.md` 为准。
- **逐行注释不要从被删的逐行解释表批量搬运**：把表里那句话原样贴到几十个行尾，检查器判“注释重复粘贴（首次 Lxxx）”，且同一句泛化解释不构成按行语义覆盖。按每行实际作用各写一句短注释，原注释逐字保留、只追加。
- `(* … *)` 头块是源文件元信息（FB 名、工程师、日期、版本、功能清单），不是可执行语句：给块注释整体一句“块注释不参与执行”即可，不要逐行追加“本行提供判断所需的配置”这类填充句，那是把注释质量门禁自己刷红。
- **严格行覆盖与注释质量是两个门槛**：`--require-every-line` 只证明“每条非空代码行都有注释”，重复/低价值仍由默认模式报。交付时两个数字分别报，不能拿一个绿了冒充另一个绿。
- 判定“某行是否需要注释”直接跑 CLI：`python3 -B scripts/check_plc_comments.py <file> --require-every-line`。别在 `execute_code` 里 import 脚本猜内部函数名——公开契约是 CLI 与 `check_text()`，其余函数会改名并抛 `AttributeError`。
- 大手册不要加 `--json`：输出上百 KB，读默认摘要行（每个围栏的覆盖数 + 首条确定性错误）就够定位，全量 JSON 只在写测试断言时用。

## 文档骨架的常见自伤

- 章节分隔串和循环各自拼了一次 `<a id="mxx"></a>` → “锚点重复”。拼完统一去重。
- 章标题 `##` 下面直接挂模块 `####` → 版式报“标题从 H2 跳到 H4”。模块标题用 `###`，或补一层章节容器。
- 表格列数、围栏闭合、长行超宽是低级但高频的失败项，生成后先跑格式/版式检查再谈内容。

## 覆盖按执行单元对账，不按行数

- 保真对账的最小单位是**可执行单元**：一行里的每个语句（`THEN x := 1; END_IF;` 记 3 个）都算一次，纯闭合行与空语句不算。源侧单元数须与文档侧逐模块单元数完全相等（同一套分词双向统计后 Counter 比对）；行数相等说明不了覆盖完整。
- 生成器与校验器共用同一套 `logical_units()`/`fences()`，别各写一份分词规则，否则会自己给自己放行。
- 用 manifest 给非执行行（归档说明、变量表、围栏、空白、历史头注释）写 `exclude` 并逐段填理由；只有 `check_code_integrity.py --final` 接受行尾追加的 ` // ` 注释，不带 `--final` 会把教学注释判成改写源码。
- 除完整性外另断言：源行被改动时文档行须以源行开头且追加部分以 ` // ` 开头；显示的行号列表须等于“本模块含可执行单元的行号列表”，两者都从源码算出，不从稿子反推。

## 覆盖对账的参照物是源文件，不是计划清单

生成器把 plan 当唯一真值：`assert ''.join(u['source'] for u in plan) == 文档拼回源码` 只在「计划本身完整」时成立。计划漏行、起点错位或只覆盖部分节时，自校验照样报 100% 覆盖，成品少整段源码而毫无提示。

- **另建一份独立来源对账**：逐归档节独立算 `source_exact`（节内源码与 plan 的 `source` 逐字符相等）和 `starts_contiguous`（节内单元起点从 1 连续走到行数结束），并报每节行数。任一项不成立是计划缺口，不是讲解缺陷，两类分别归因。
- **反例要手跑，不要推理**：把 plan 的 `start` 改成越界值、再让独立源文件比 plan 多几行，生成器仍应能走完准备阶段（`complete:false` 只表示没生成，不表示来源对账通过）。把「准备通过」读成「来源无误」是这里最常见的假绿。
- 报覆盖带三个数：归档节数及各节行数、plan 单元数、逐节 `source_exact` 结果。只说「45/45 单元完成」无法区分「计划完整」和「计划漏掉原始文件的一半」。

## 一次真实长跑要报的四个数

单次完整生成只能证明这一次跑通，报数要让下一轮能判断稳定性：

- 已接收单元/总单元，外加「第几次尝试被接收」的分布——大量第 3 次才接收说明提示词或校验过紧，不能只记成模型差。
- 拒收原因按类计数（JSON 解析失败、尾注值校验、schema），并说明是局部重试还是整批重发。
- 三种状态分开写：格式通过、源码对账通过、语义审校（pending 就是 pending）；「N/N 完成」不等于手册合格。
- 成品 sha256 与字节数，便于下一轮确认交的是修订后那份。

## 原文触发关键词扫描：如实报残留，不改源

`validate_handbook` 的只读安全扫描按关键词匹配全文，不区分“模型建议”与“被讲解的原注释”。原 PLC 注释里出现“强制”“旁路”一类词会稳定命中，而源码保真禁止改动原注释。

- 不为刷绿删改原注释，也不把该项报成通过：交付说明点明“N 处命中来自被保留的原注释”，其余检查列真实结果。
- 验收标准是“本次讲解未新增命中”，不是“命中为零”。

## 给讲解质量加机器门槛：字段取值与误报

把“处理过程/关键逻辑/状态变化不得写空话”从规范变成校验器必拒项时，先解决取字段，否则好稿先被拦死。

- **不要用屏蔽视图的字符偏移切原始文本**。`body_view()` 把围栏内容替换成占位符，字符长度与原文不同；在它上面 `finditer` 得到的位置再拿去切 raw 会整体错位，表现为“字段明明写了却报缺失”。改为两版都 `splitlines()`，在屏蔽行上只求**行号**，再按行号切原始行；两侧行数不等就退回原始行。
- **字段内容有四种合法形态**，取值要全部覆盖：同行一段话；字段名后空行、正文写在下一段的列表或段落；字段名带括号注释（`**关键逻辑**（为什么只检测一次）：`）；字段内容就是一段代码对照。只按“同行剩余部分”取，会把后三种全判成空。
- 遇到围栏就跳过代码行；若整段没有正文，**回退用代码内注释当字段内容**——作者把解释写进 `//` 也是解释，不该判缺失。正文与代码都为空才算缺陷。
- **真正的门槛是空话清单，不是字数**。长度阈值放到 10 字左右即可；15 字以上会误杀“工件从传送带进入工位”这类合法短场景设定。命中的是 `执行判断`、`满足条件则赋值`、`条件很重要`、`变量变化了`、`详见代码`、`根据控制目标` 这类短语。
- 做子串匹配前先看中文单字陷阱：`略` 会命中 `策略`，`同上` 相对安全但要有意识。空话项一律用多字短语，并在清洗（去空白与标点、转小写）后的文本上比较。
- **新质量检查要同时过正例和拒坏例**：当前规范样例必须 0 错误；再把同一份稿的字段替换成空话，必须报出对应字段。正例失败时改校验器，不要改稿子去迁就；坏例不失败说明检查没生效。
- 报错信息带修法（“请写清输入→判断→结果与必要性”），不写“缺少内容”。返工方向明确，才不会退回空话。

## 输出上限类门槛会诱导模型删内容

只要加“超过 N 行判错”，弱模型就会**删掉几行让块变小**来合规，而不是按逻辑拆分——结果是源码缺行，比不合规更糟。

- 报错文案必须双向写死：`按逻辑边界拆成多段…严禁删除、截短或用省略号代替源码`。只写“拆成小段”等于给了删除这条路。
- 上限要留出正常讲解的余量：单个教学块 25 行、按逻辑 3～8 行；定得比实际写法更紧，会逼模型在“合规”和“讲全”之间二选一。
- 校验器只管上限，**不保证没删行**；源码完整性仍靠 `check_code_integrity` 对账。上限检查与完整性检查要同时存在，缺一个就能被绕过。
- 弱模型（flash 级）面对长 skill + 多重门槛时，优先丢的正是代码。给它 `references/one-page-prompt.md` 那种一页契约（规则 ≤6 条、骨架固定、源码保真第一条），不要再往大 skill 上加规则。

## 第一性原理的机器代理：只查需要论证的字段

“是否讲了为什么”无法直接判定，可用因果连接词做代理（因为/因此/所以/否则/若/如果/才能/必须/避免/会导致…）。

- 只对 **设计依据** 与 **关键逻辑** 生效。**状态变化** 本质是状态清单（`FALSE → TRUE`、`由第5段清除`），天然没有因果词，套上去必然误杀。
- 空字段先报“缺失”，再报“没有推导”，不要让两条错误叠在同一处。
- 拒绝文案给出可用词（“用因为/因此/否则/会…说明删改后果”），否则模型只会加一句“因为这样比较好”。
- **因果词必须落在该字段自身的文本里**：取值只截字段名到下一个字段名之间的正文，紧邻段落、上方表格或代码里的理由都不算。写成“**关键逻辑**：A 只替代 X，不替代整组门槛。因为这条 OR 被括号限制在该组内，所以…”，同一段内既给结论也给因果；把推导放到另一段、字段本身仍是纯描述，判错不变。

## 注释版交付的两步校验

用户要求源码内逐行尾注时，“结构合法”与“源码保真”是两件必须分开证的事，只能各自证自己。

- **结构/局部契约检查在剥离尾注的副本上跑**：按 `^(.*) // AI: .*$` 还原成原行另存一份副本，再送 `check_local_explanation.py` 一类检查；通过只代表结构与剥离后正文合法，不代表原码也一致。
- **源码保真单独比对**：从归档原文重新切片，与交付围栏逐块去掉尾注后逐字符比较，不靠生成器对自身清单自校验。两项都跑过才算交付核实，缺一项不能顶替另一项。
- 交付说明按实写：结构检查在哪份副本上通过、源码保真如何独立比对、语义审查/编译/仿真仍未做。

## 模板文档自身的两个坑

- 在 Markdown 里写“可复制提示词”时，提示词内部的 ```st 会闭合外层 ```，`check_plc_comments` 报“PLC 围栏被外层围栏吞没 / 围栏未闭合”。外层用四个反引号包住。
- 在 references 下新增规范文件、或在 evals 下新增测试文件，都必须在 `references/catalog.md` 登记，否则 `validate_skill --strict` 直接报“catalog 未登记资产”。先登记再跑全量，省一轮返工。

## 出多版式对比稿：只换阅读编排，不换内容

为同一对象生成 A/B/C 三种对比版式时，三份的差别只在模块内部阅读编排（A 代码与解释交替、B 整块源码后集中说明、C 模块路线图加分支精讲）。内容必须逐项对齐，否则用户比较的是内容差异而不是版式。

- **一次提取，三处渲染**：把归档解析成 `module_data`（关键变量、功能定位、源码块与紧邻说明、整体讲解四字段、示例、交接、审查），三个 `build_x(m)` 只重排这些字段；prefix（封面/目录/章1–3）与 suffix（ch5 及以后）原样共用，不各写一遍。
- **对齐断言写进生成器**：三份的模块数、源码行数、尾注数、五部分小节名一律相等，且每模块围栏拼回后与归档对应节逐字符一致（剥离 ` // AI: ` 后比较）。任一份少一行或差一句，就不是版式差异。
- **标题层级按各自版式适配**：B 把功能段说明降为 `#####` 挂在 `#### 功能段说明` 下；A/C 保留归档原有 `####` 分块结构。不要把一版的标题层级直接套到另一版，否则版式检查报“标题跳级”。
- **交付只报已验证项**：源码一致与注释门禁为真是硬结果；语义审查、编译、实机仍是未做，不能写成“三份都通过”。

## 五部分版式按指定逻辑颗粒度展开

采用五部分结构且要求每个逻辑段都有解释、示例与交接时，保留六列变量表、五部分和整体讲解四字段，把它们的重复单位从整节缩为完整逻辑段。先交候选模板与相邻真实逻辑段的填实示例，不以版式名称替代颗粒度要求，避免整节贴码后仅给一组示例，也不只补表情后宣称完成。每段按变量→定位→源码→四字段解释→具体纸面示例→交接→审查与验证展开，再进入下一段；跨段的写入覆盖与实际调用证据分别说明。表情按栏目固定，模块内层级统一，原模板正文只增补不删并；候选稿在仓库外保存，未明确接入时不覆盖已登记模板。

## 段落合并后的验证边界

- 清理多余空行时先隔离源码围栏，只规范化正文；对整份 Markdown 做 `re.sub(r'\n{3,}', '\n\n', text)` 会删原码空行，即使逻辑没变也破坏逐字符保真。按节独立对账与全量拼回都必须做。
- 例子若逐行改变条件但前一行已置位锁存，应明确是每行重置前态的独立场景；连续调用必须承接锁存入口，不能让已退出的分支在第二行继续运行。
- 分支片段不写不代表整条选择结构不写；恒假首支之后仍可有 ELSIF 写点，结果表必须声明观察边界。
- 仓库外生成器导入仓库模块前设 `sys.dont_write_bytecode=True` 或以 `python -B` 启动；自动生成的 `__pycache__` 会被候选隐私扫描和隔离回归当成非文本材料，不能靠忽略测试掩盖。

## 尾注是位置绑定的数据，不能全局字符串替换

批量改“注释重复粘贴”时最容易走的错路是 `text.replace(旧尾注, 新尾注)` 全量替换。同一句在不同行承担的行语义不同，全局替换会把角色贴错：本站 `Station1` 的解释被搬到 `Station2` 行、`ELSIF … AND Done` 写成“本FB尚未Done”。检查器只报“重复”、不报“讲错”，错注释会静默进稿。

- **先按顺序还原基准行**：从归档逐模块按出现顺序取行（`pos` 游标 + `assert pos == len(base_lines)`），确认每条尾注回到它原本对应的源行，再改措辞。
- **用状态机取上下文，再拼句子**：扫本模块源码块维护 `active`（如 `双料分支`／`单路分支`）、`branch`（`首支`／`ELSIF`）、`result`（`结果N`）、`st`（由当前行出现的 `Station1`／`Station2` 结构名决定），据此生成句子。**站点名必须来自该行自身**，不能沿用上一行。
- `check_plc_comments.py` 的“注释重复粘贴（首次 Lxxx）”会给出配对行号，逐对回看源码就能发现贴错；它只保证不重复，语义对错仍要按分支人工核对。

## 校验收敛顺序

局部追加注释版用 `check_local_explanation.py --allow-ai-tails`，按输入原行完整前缀识别本轮尾注，不用全局正则截断作者注释或字符串中的 `// AI:`。为此保留反例：改原语句、删作者标记、空尾注、换行变更都必须拒收。模型烟测同时核对方向列来自声明、连续轨迹承接前次后值、命名用途不越过推断边界；机械通过不能替代这三项。

先跑 `check_plc_comments` 与 `validate_st_rendering`（管源码保真与注释覆盖，会因分段切点反复报错，改切点即可全绿），再跑 `validate_handbook`（管模板小节、覆盖清单、元信息）。后者的错误量常远大于前者且多半来自结构与模板不一致，不是内容错误——先分清这两类，别用改内容的方式去糊结构问题。

`validate_handbook` 对模块小节名与清单字段是硬要求。用户明确要另一种讲解形态时，先确认是要改模板还是接受该项不通过，并把未通过项如实报给用户，不把“部分通过”说成通过。

## 校验器要先按文档模式分叉，再判内容

版式校验须按文档模式选择契约。局部与完整手册的适用结构不同，误用局部契约可能使合法手册被拒；应分别判断工具适用范围与文档质量。

- 模式由 `mode`/元信息判定（`文档类型：handbook`）。当前局部与HBK共享五部分名称和顺序，通过共享常量维护；全局章节与局部单模块检查按模式分开，不能拿旧局部四部分判现行产物。
- 模块编号正则按模式放宽：handbook 允许 `B0`、`B1` 这类原始工程编号，不能只认 `M\d{2}`；覆盖清单对账也要接受同一套编号。
- 25 行教学块上限只约束“拆段讲解”的局部模式；完整手册整块保留原码是模板要求，此时保真由 `check_code_integrity` 负责，行数门槛跳过。两处规则并存，任何一处单向收紧都会把合规稿判死。
- 只读安全扫描要跳过 PLC 源码围栏：原注释里的“强制屏蔽”“旁路”是数据不是指令，按全文关键词扫描会稳定误报。做法是先按围栏把源码段抹空再扫正文，正文里的操作建议仍必须拦住——别为了消误报把整条安全门禁关掉。
- 改完工具只意味着“该类误报消失”，不等于“文档通过”。仍报错的项照实列给用户，并说明是工具尚未兼容还是稿件确有结构缺陷。

## 修订既有成品：只删用户点名的那一项

要求从指定既有版本仅删除某项时，交付物是**指定源文件减去目标内容**，其余正文保持，不按当前模板另行重建。

- 先定位到底指哪一份文件（归档目录、CHANGELOG、历史产物），把它复制成新文件名再改；不混用不同版本或生成器输出凭记忆复原。
- 删除范围要可证明：改前统计被删项的数量（如 10 处独立逐行表），改后同一统计为 0，同时逐字比对源码块证明未被改动、块数不变，两个数一起报。
- 目录、元信息、版本说明里对被删项的计数描述同步删掉，否则文档自相矛盾。
- 不顺手重写讲解、不重排编号、不把结构校验器的旧契约一起改掉；原先就失败的项目如实报为既有失败，不冒充本次通过。
- 同一任务追加逐行注释要求时，以已完成定点删除的稿件为底稿增量追加，保留已确认的其他改动。

## 长稿不要外包给子代理一次写完

整份长手册交给子代理生成，容易在中途被中断且产出未经校验；父代理用生成器拼装、自己跑校验，能定位到具体行。子代理更适合只读的事实复核（长条件优先级、生命周期、取值错误），复核结果再由父代理落到正文。

## 改造生成机制：模板同源、父全子小、证据分层

当前单元表达沿用简约五部分：六列变量表前置、原码与短业务尾注、整体讲解四字段、一个具体示例、交接及适用审查/验证状态；外层加章与模块目录。模板正文、`inline-comment-style.md`（含命名推断）及匹配的 `inline-comment-examples.md` 案例须进入每个独立生成请求；同会话可复用仍可见参考，恢复/压缩后重新加载。状态文件连同模板与源码记录参考摘要，防止同一手册混用新旧表达规范。写前加载只证明输入前置，不等于模型遵守或语义通过，仍按下列分层验收。

建设模板复用、嵌套与长文稳定生成能力时，改的是机制，不是某份稿子。四条按顺序落实。

1. **模板与渲染器只留一处版式定义**。同一套栏目既有 `.md` 模板文档又有 Python 渲染器时，两处各写一遍必然漂移——改模板不改脚本、加脚本不改模板，补提示词和检查器都治不了根。做法：模板资产（章节骨架、栏目标题与顺序、槽位）作为唯一真值，渲染器只做槽位填充与拼接；再用一条测试断言“改模板标题 → 最终 md 结构随之变化”，证明控制权真的在模板上，而不只是 `render()` 返回串变了。
2. **三层组合：文档 → 章/模块 → 讲解单元**。父级承载标题、范围、目录、模块引入与小结，叶子是“一段源码 + 五部分正文”。生成时把完整父结构当上下文传下去，但每次只让模型输出一个小单元；不要让它一次写整本，也不要按固定 3 段机械切批——那样会把同一个外层 `IF/ELSIF` 的入口、各分支和后续写点拆散，漏掉外层条件。
3. **续接是状态机的产物，不是让模型自己“接着上文写”**。每个单元落盘时写入状态文件（已完成编号、下一批起点、已接收单元的源码哈希、模板版本），新进程从状态续跑；续跑前校验模板与 layout 未变，变了就拒续。已接收单元的字节不应再变，也不应重发。
4. **验收分两层报，不能互相冒名**。程序机制测试只证明切分、拼装、拒收、恢复这些代码路径；真实模型试跑才证明提示词与模板在模型上稳定。前者过了就写“机制通过、模型未验证”，不要合成成“长文已稳定”。

### 夹具要真的难，否则测的是循环次数

最容易出现的假验收：长文夹具是 60 个各一行赋值的小片段、父上下文只有一句话。这种夹具只证明“拼接循环跑了 60 次”，没测到真正的难点——父结构远大于单元输出。合成长文至少要有：多层嵌套 `IF/CASE`、块注释、字符串里带 `//` 与 HTML 字面量、单个模块父结构上百行；同时断言每个 prompt 里确实带着完整模块父结构。

### 失败与恢复要有原始证据

- 截断重试只能重试未接收的单元，不能整批重发；`rejected.json`、原始响应与失败样本原样保留，不修补后冒充成功。
- 恢复证据是真实的进程退出与新进程续跑记录（已接收单元哈希不变、未重复插入），不是同进程里重置一个变量。
- 最终合并另出一份报告：计划节点各出现一次、无重复编号、无孤儿、锚点有效、源码按序回拼。

### 别在改机制时修内容

审稿报告里的 PLC 语义结论即便成立，也属于“内容问题”，单列交付；拿它去改模板、改批次或加领域规则，会越出机制改造范围，混淆模板职责与具体稿件语义。反过来，机制测试全绿也不能声称讲解正确。
