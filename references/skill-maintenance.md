# 技能维护入口（仅维护/审计时加载）

本文件承接 `SKILL.md` 维护入口的原文细则与迁移历史，仅在修改技能、审计仓库或核对历史版本时读取；普通 PLC 讲解不加载。条件路由仍保留在入口，规则本身不因下沉而失效。

## 仓库维护操作

仅维护技能/审计时，读取 `references/workflow.md` 的“技能维护与成果保护”，再按实际任务读取“版本与 Git 管理”“技能维护回归”“入口与契约回归”“行为微测的验收口径”“测试夹具与真实归档的可行性预审”或“交付包复测”等命名维护节执行；日常讲解不加载维护记录或历史对话。

**先确认改的是代码仓库还是已安装副本。** 用户说“改这个技能”时，`~/projects/<skill-name>` 这类存放模板、规则与 `evals/` 的仓库才是真身，`~/.hermes/skills/.../<skill>` 只是安装副本。同名时先核对该仓库的分支与 `git status`，再决定是否同步安装副本；不默认打开安装目录改，也不把安装目录里的旧版当待改对象。

**改模板/生成机制时，交付物是机制不是某一份讲解稿。** 用户说“改模板/改生成方式/长文不稳定/按我原技能的长文方式来改造”时，范围是模板资产、切分与批次、断点续接、最终合并与校验；不要顺手修某份稿子的 PLC 语义，也不要把语义审查报告当成改造依据。出现语义疑点只单列成内容问题，不据此改模板或加领域规则。改造优先**复用本技能已有的长文流程**（清点全范围 → 按完整闭合逻辑分段 → 逐批落盘并记下一起点 → 自动续接 → 稳定编号合并校验），新机制只补真实缺口（模板与渲染器同源、父结构上下文与小单元输出分离、失败与恢复可核查），不另造一套并行的生成流程。用户连续纠正方向（“不是让你修内容”“按我原来的方式”）时，先停下当前改动、复述范围再动手，不要用更多同类改动证明进度。

**在用户未提交的工作树里改技能，先留基线再改。** 委派前记录白名单文件的 sha256 清单、`HEAD`、暂存区快照与 `git status`；改完复算，只允许白名单内路径变化、`HEAD` 与暂存区不变，并把本轮改动做成可反向应用的补丁。全程不 reset/revert/checkout/clean，也不 add/commit/fetch，用户其它未提交改动原样保留——「改完发现范围不对」时唯一的补救是报告差异，不是回滚工作树。

**增删规则先枚举全部承载点**：`SKILL.md`、对应 `references/` 正文、`catalog.md` 规则登记、`CHANGELOG.md`、`evals/` 断言与**夹具的 Acceptance checklist**、`templates/` 与 `examples/` 里内嵌的自检项。夹具验收清单和样稿自检项最容易漏，改完入口仍会被旧口径继续判分。只改入口会让旧规则从参考文件或测试里继续生效；改完用 `search_files` 反查旧表述，确认为 0 命中再报完成。**描述自身状态的句子也算旧表述**：写完“入口仍按旧契约、尚未接入、留待后续授权”这类进度句，一旦真的接入就必须同步删除或改写，否则文档里留下一句自我否认的假话（候选仓库与已安装版分居两处时尤其容易只改一边）。版本号升级只精确替换目标行，禁止 `replace_all`——catalog 的规则行与用例行常同时含旧版本号，全局替换会把两处一起改错。`patch` 返回“Non-exact match”时必须读 diff 核对边界：编号/列表块会被整段复制或吞掉一条，改完立即读回确认编号连续、条目不重复。

**`skill_manage` 的一次批量操作是原子的。** 任一 op 失败（例如某个 `patch` 的 `old_string` 不存在）会整批回滚，前面成功的 op 也不会落地。把新增参考文件（`write_file`）与正文/目录补丁拆成不同调用，失败时按返回逐条重放；不能因为“返回里有成功项”就以为已写入。

## 历史模板改造记录（仅维护时读取）

以下为 3.22.x 时期模板改造的验收记录，保留原文以说明当时的三件交付与 ZIP 证据边界；不进入日常答复，也不代表当前版本仍待接入。

**模板改造的核心目标：** 用户要求稳定生成标准化讲解文档，不能将开发重心降成证明模型具备基本代码解释能力。用户指定 3.22.17 时，从该 ZIP 的 `template-handbook.md`、`example-block-handbook.md`、`handbook-guide.md` 提取真实骨架，保留变量前置、模块五部分、整体讲解四字段，再融合当前初学者、`AI:`、批判审查和嵌套分块需求。该 ZIP 不含 `local-code-explanation.md`，不可引用已安装较新版本的同名文件冒作旧版证据。旧模板五列变量表与指南六列规范冲突时采用六列；将当前写法必要性、优势、保持和复位的断言改为证据支持的条件结论或未知，不为填栏目补事实。第一阶段的交付是**一体的三件**：完整处理流程（输入判型 → 工程/片段定位 → 声明·类型·实例核对 → 调用与读写追踪 → 因果分析 → 按模板讲解 → 独立批判审查 → 分层验证交付）、两份融合模板、两份填实样稿。只交模板等于交了空骨架——用户会立刻追问「针对一段代码的完整流程呢」，而这正是他要固化的东西；反之只交流程不交填实样稿，用户无法判断栏目填出来是什么样。入口接入（SKILL.md 路由与阶段 2/3）放到下一阶段；品牌及平台安装分发按用户指定后置。
