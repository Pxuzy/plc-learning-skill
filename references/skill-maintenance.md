# 技能维护入口（仅维护/审计时加载）

本文件说明 `SKILL.md` 维护入口的操作细则，仅在修改技能、审计仓库或核对模板时读取；普通 PLC 讲解不加载。入口负责条件路由，本文件负责维护与验收。

## 仓库维护操作

仅维护技能/审计时，读取 `references/workflow.md` 的“技能维护与成果保护”，再按实际任务读取“版本与 Git 管理”“技能维护回归”“入口与契约回归”“行为微测的验收口径”“测试夹具与真实归档的可行性预审”或“交付包复测”等命名维护节执行；日常讲解不加载维护记录或历史对话。

**先确认改的是代码仓库还是已安装副本。** 修改技能前，先定位存放模板、规则与 `evals/` 的代码仓库；`~/.hermes/skills/.../<skill>` 是安装副本。同名时先核对该仓库的分支与 `git status`，再决定是否同步安装副本；不默认打开安装目录改，也不把安装目录里的旧版当待改对象。

**改模板/生成机制时，交付物是机制不是某一份讲解稿。** 用户要求改模板、生成方式或长文稳定性时，范围是模板资产、切分与批次、断点续接、最终合并与校验；不要顺手修某份稿子的 PLC 语义，也不要把语义审查报告当成改造依据。出现语义疑点只单列成内容问题，不据此改模板或加领域规则。改造优先**复用本技能已有的长文流程**（清点全范围 → 按完整闭合逻辑分段 → 逐批落盘并记下一起点 → 自动续接 → 稳定编号合并校验），新机制只补真实缺口（模板与渲染器同源、父结构上下文与小单元输出分离、失败与恢复可核查），不另造一套并行的生成流程。用户连续纠正方向时，先停下当前改动、复述范围再动手，不要用更多同类改动证明进度。

**在用户未提交的工作树里改技能，先留基线再改。** 委派前记录白名单文件的 sha256 清单、`HEAD`、暂存区快照与 `git status`；改完复算，只允许白名单内路径变化、`HEAD` 与暂存区不变，并把本轮改动做成可反向应用的补丁。全程不 reset/revert/checkout/clean，也不 add/commit/fetch，用户其它未提交改动原样保留——「改完发现范围不对」时唯一的补救是报告差异，不是回滚工作树。

**增删规则先枚举全部承载点**：`SKILL.md`、对应 `references/` 正文、`catalog.md` 规则登记、`CHANGELOG.md`、`evals/` 断言与**夹具的 Acceptance checklist**、`templates/` 与 `examples/` 里内嵌的自检项。夹具验收清单和样稿自检项最容易漏，改完入口仍会被旧口径继续判分。只改入口会让旧规则从参考文件或测试里继续生效；改完用 `search_files` 反查旧表述，确认为 0 命中再报完成。**描述自身状态的句子也算旧表述**：写完“入口仍按旧契约、尚未接入、留待后续授权”这类进度句，一旦真的接入就必须同步删除或改写，否则文档里留下一句自我否认的假话（候选仓库与已安装版分居两处时尤其容易只改一边）。版本号升级只精确替换目标行，禁止 `replace_all`——catalog 的规则行与用例行常同时含旧版本号，全局替换会把两处一起改错。`patch` 返回“Non-exact match”时必须读 diff 核对边界：编号/列表块会被整段复制或吞掉一条，改完立即读回确认编号连续、条目不重复。

**`skill_manage` 的一次批量操作是原子的。** 任一 op 失败（例如某个 `patch` 的 `old_string` 不存在）会整批回滚，前面成功的 op 也不会落地。把新增参考文件（`write_file`）与正文/目录补丁拆成不同调用，失败时按返回逐条重放；不能因为“返回里有成功项”就以为已写入。

## 模板改造的验收要求

模板改造以稳定生成标准化讲解文档为目标，不能降成证明模型具备基本代码解释能力。以用户指定的真实模板和成品为依据，保留变量前置、模块五部分、整体讲解四字段，并核对初学者解释、行内注释、批判性审查和嵌套分块需求。指定资料缺少某文件时不得借用其它副本冒充来源；字段冲突须查明权威，不为填栏目补事实。写法必要性、收益、保持和复位等断言只写证据支持的条件结论或未知。

机制改造交付包括完整处理流程、对应模板和填实样稿：输入判型 → 工程/片段定位 → 声明、类型及实例核对 → 调用与读写追踪 → 因果分析 → 按模板讲解 → 独立批判性审查 → 分层验证交付。只交空模板不足以检验实际效果，只交流程也不能替代样稿。接入当前入口、样例与检查器时核对一致性，平台安装与分发按用户授权执行。
