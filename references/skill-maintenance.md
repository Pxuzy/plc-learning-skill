# 技能维护入口（仅维护/审计时加载）

本文件说明 `SKILL.md` 维护入口的操作细则，仅在修改技能、审计仓库或核对模板时读取；普通 PLC 讲解不加载。入口负责条件路由，本文件负责维护与验收。

## 仓库维护操作

仅维护技能/审计时，读取 `workflow.md` 的“技能维护与成果保护”，再按实际任务读取“版本与 Git 管理”“技能维护回归”“入口与契约回归”“行为微测的验收口径”“测试夹具与真实归档的可行性预审”或“交付包复测”等命名维护节执行；日常讲解不加载维护记录或历史对话。

**先确认改的是代码仓库还是已安装副本。** 修改技能前，先定位存放模板、规则与 `evals/` 的代码仓库；`~/.hermes/skills/.../<skill>` 是安装副本。同名时先核对该仓库的分支与 `git status`，再决定是否同步安装副本；不默认打开安装目录改，也不把安装目录里的旧版当待改对象。

**改模板/生成机制时，交付物是机制不是某一份讲解稿。** 用户要求改模板、生成方式或长文稳定性时，范围是模板资产、切分与批次、断点续接、最终合并与校验；不要顺手修某份稿子的 PLC 语义，也不要把语义审查报告当成改造依据。出现语义疑点只单列成内容问题，不据此改模板或加领域规则。改造优先**复用本技能已有的长文流程**（清点全范围 → 按完整闭合逻辑分段 → 逐批落盘并记下一起点 → 自动续接 → 稳定编号合并校验），新机制只补真实缺口（模板与渲染器同源、父结构上下文与小单元输出分离、失败与恢复可核查），不另造一套并行的生成流程。用户连续纠正方向时，先停下当前改动、复述范围再动手，不要用更多同类改动证明进度。

**在用户未提交的工作树里改技能，先留基线再改。** 委派前记录白名单文件的 sha256 清单、`HEAD`、暂存区快照与 `git status`；改完复算，只允许白名单内路径变化、`HEAD` 与暂存区不变，并把本轮改动做成可反向应用的补丁。全程不 reset/revert/checkout/clean，也不 add/commit/fetch，用户其它未提交改动原样保留——「改完发现范围不对」时唯一的补救是报告差异，不是回滚工作树。

**增删规则先枚举全部承载点**：`SKILL.md`、对应 `references/` 正文、`catalog.md` 规则登记、`CHANGELOG.md`、`evals/` 断言与**夹具的 Acceptance checklist**、`templates/` 与 `examples/` 里内嵌的自检项。夹具验收清单和样稿自检项最容易漏，改完入口仍会被旧口径继续判分。

只改入口会让旧规则从参考文件或测试里继续生效；改完用 `search_files` 反查旧表述，确认为 0 命中再报完成。**描述自身状态的句子也算旧表述**：写完“入口仍按旧契约、尚未接入、留待后续授权”这类进度句，一旦真的接入就必须同步删除或改写，否则文档里留下一句自我否认的假话（候选仓库与已安装版分居两处时尤其容易只改一边）。版本号升级只精确替换目标行，禁止 `replace_all`——catalog 的规则行与用例行常同时含旧版本号，全局替换会把两处一起改错。

`patch` 返回“Non-exact match”时必须读 diff 核对边界：编号/列表块会被整段复制或吞掉一条，改完立即读回确认编号连续、条目不重复。

**`skill_manage` 的一次批量操作是原子的。** 任一 op 失败（例如某个 `patch` 的 `old_string` 不存在）会整批回滚，前面成功的 op 也不会落地。把新增参考文件（`write_file`）与正文/目录补丁拆成不同调用，失败时按返回逐条重放；不能因为“返回里有成功项”就以为已写入。

## 模板改造的验收要求

模板改造以稳定生成标准化讲解文档为目标，不能降成证明模型具备基本代码解释能力。以用户指定的真实模板和成品为依据，保留变量前置、模块五部分、整体讲解四字段，并核对初学者解释、行内注释、批判性审查和嵌套分块需求。指定资料缺少某文件时不得借用其它副本冒充来源；字段冲突须查明权威，不为填栏目补事实。写法必要性、收益、保持和复位等断言只写证据支持的条件结论或未知。

机制改造交付包括完整处理流程、对应模板和填实样稿：输入判型 → 工程/片段定位 → 声明、类型及实例核对 → 调用与读写追踪 → 因果分析 → 按模板讲解 → 独立批判性审查 → 分层验证交付。只交空模板不足以检验实际效果，只交流程也不能替代样稿。接入当前入口、样例与检查器时核对一致性，平台安装与分发按用户授权执行。


## 生成机制与试跑的维护方法

**换模型试跑技能时**：执行 [隔离试跑与证据核对](skill-model-trial.md)。本节只负责维护路由，不另行定义试跑台、工具集或出稿判定。

**渲染器报错先落到字段。** 模板渲染器通常逐字段做非空/无标题/无围栏检查，抛出的 `ValueError('field:<键>')` 才指得准；命令行常把异常压成一句“invalid-or-output-exists”，还把“输出已存在”混在同一条里。要定位就在 Python 里 import 调 `render()`，别读命令行那句话；字段意外为空，先查切片锚是否命中而不是改内容。

**改造生成器（模板组合、分批、续接）后**：执行 `skill-model-trial.md` 的“生成器改造的真实样本验收”和“门禁本身要被反例测试”；各层分别报告，不以维护回归替代真实模型样本。

**模板设计与试讲验收须提供可审阅资产。** 交付是资产＋样稿＋对照表：写作规则（每栏写什么、边界在哪、证据等级怎么标）＋骨架模板文件（文档级与段落级）＋用真实源码生成的试讲样稿＋一张“需求 → 落在模板哪一处（章节/字段/校验）→ 测试结果”的对照表。模板必须逐条对应当前全部有效需求；仅有版式概括不算完成，已排除的方案不列为待实施项。样稿选结构彼此不同的真实模块各一段（短 `IF`、定时器、多条件判断、嵌套 `IF` 加条件外赋值），最后一类专门检验能否讲对“哪些语句受条件控制”，这是栏目齐全也最容易讲错的地方。候选资产放仓库外 scratch，不动已安装技能与源码，用户确认结构后再接入。

**模板校验器自己也要有反例集**：删掉一个字段正文、删一个小节、删一个模块、改动源码一个字符、把表格少写一列、把一个锚点链接改断、把正文藏进 `<!-- -->`、**把表头行插进变量数据行**，逐项自动跑并断言被拒；反例通过（被错误接受）比正向稿失败更严重。每加一道新门禁就立刻配一条它的反例——只做正向验证的门禁会把「结构上看起来对」的脏数据放行（表头混进数据行、变量名只写裸成员名都属这类）。

委派外部执行器做全篇重写时，任务书必须写成“直接落地全文、禁止再探索、禁止只出计划”，并在监视里盯第一个正文写入时间；若十多分钟只在反复读源稿与列计划、既无稿件文件也无正文写入，停掉这条会话，保留已产出材料后换更窄的任务重派，不要靠轮询等它自己想通。

## 维护树与默认运行包

维护树保留历史兼容与研发资产：`references/example-handbook.md`、`references/example-fb.md`、`scripts/legacy_handbook_validator.py`、`references/external/README.md`；它们不随默认运行包提供，不是日常讲解前置条件。运行包不承诺旧 `--source/--handbook` CLI，当前手册检查使用 `scripts/validate_handbook.py`。需要历史兼容或研发资料时在完整维护树读取，不在精简包中追索缺失文件。运行包分发不得产生指向省略资产的读者链接。
