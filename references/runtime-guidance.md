## 归档来源与局部深讲

**从既有归档讲解时**：先读归档目录的 `归档校验.json`，以其中的 `sections[].status`、`missing_sections_parts`、`sha256` 作为完整性与来源的真值——`partial` 节只讲可见部分并在节内标缺口，`missing_sections_parts` 逐条列入文末缺口，源文件哈希与记录不符即视为来源变更、不按旧结论继续。解释用「节N + 行号范围」引用原码，不把整份源码再贴成第二副本（用户要原码时才附）；归档头部的私有标识（UUID 类 XML 名、人员字段）不复现，只写归档路径并声明未核对 XML 原件。

- **B.** 要读懂一个局部代码块：按 SKILL.md 的来源门禁核验，先加载 `local-code-explanation.md`，采用五部分块级局部讲解模板；关键变量前置，五部分依次为“功能定位与执行条件 → 源码 → 代码块整体讲解 → 形象示例 → 程序交互与段间交接”。

  本模式以该参考的源码呈现和表情规则为准：保留原码及原注释，**默认逐行附简洁业务短注释**（空白行与纯注释行除外，不需要用户再次要求），按本文件“输入路由与模板组合”中的“注释前置参考”加载规则与案例；用户当次明确要求原样源码时不追加。行尾按原作者式短句说明对象、动作和结果，详细推演仍放正文。

  明确要求详细、新手、为什么或第一性原理时走局部块级深讲；有序读取：先完整读上述局部参考，深讲再按实际标题只取 `code-reading.md` 中“每小段按第一性原理推导”的适用分析方法和 `teaching-from-scratch.md` 中“源码深讲模式（读真实工程时加载）”的适用源码覆盖方法，最后出稿核对 `quality-checklist.md`；按标题读取必须断言区段非空，普通 B 不加载新手覆盖方法、工程索引或 catalog；只有当次明确要求逐行答疑才在正文逐项回答，保留块级因果、跨扫描、删改反例及上下游交接，明确要求详细时深度不缩水。

  保留源码，区分已确认/推断/未知，不编造地址和机械动作。

## 输入路由与模板组合

仅 C 完整手册的模板组合先查 `template-index.md`；B 严格走选择器有序路线，不经工程索引；catalog 仅在维护/审计或资产查询时加载，不整目录读。

| 用户意图 / 输入 | 路由与动作 |
|---|---|
| 只问事实、条件、变量或短代码片段 | `A`：直接回答；涉及代码按上方推导路径，保留最小安全底线 |
| 只读懂一个局部代码块 | `B`：先核验；只在歧义或要求先核对时暂停，统一用五部分块级模板与默认逐行注释的源码，明确深讲时展开同一骨架 |
| 原生工程 / 归档 / 解包目录 / 结构化导出 | 按 `workflows/read-project.md` 识别品牌、产品线、格式和版本，经 `vendors/README.md` 匹配经验，恢复原生结构并映射源码；已确认 Omron NJ/NX SMC2 才参考 `omron-smc2-xml-workflow.md`，不把解包目录默认当欧姆龙 |
| 先梳理结构 / 先知道整体怎么跑 | `OVR` → `MAP`；输出 `00-总览.md` 与 `10-结构.md`；需要统计时用 catalog 中的 survey 工具 |
| 只要原样留档源码 | 按 `source-archive.md` 逐节保真、标缺口、对账建索引；不补写逻辑 |
| 从零写 / 带练 / 练编程 | 按 `teaching-from-scratch.md` 逐阶增加一个可验证行为，交单份教程 |
| 复杂框架理解 / 整体拆解 / 完整手册 | `C + HBK`：按 `workflow.md` 分阶段带学并形成手册；真实源码新手讲解须加载 `teaching-from-scratch` 的“源码深讲模式” |
| ST / FB、FC、MFB、POU | `HBK+ST` / `HBK+FB`；同对象可按证据组合，不重复源码 |
| 状态机、步序 / 接口、实例差异 | `HBK+STATE` / `HBK+INTERFACE` |
| 工艺动作 / 信号流 / 各段怎么连 | `HBK+FLOW`；段间关系含数据、顺序、状态/步序、互锁、异常五类 |
| 多对象拆册 / 分批写 | `BOOKSET+多份 HBK`；批次与合并规则见 `workflow.md` |
| 结构过期 / 程序改版 | catalog 的漂移检查 / 导出差异工具；只报告变化，未变标 `未变`，编号不重排 |
| 生成预览 | 用真实资料在 scratch 出稿，以绝对路径校验后发文件、说明格式差异；不改/提交技能 |
| 这个 skill 有哪些模板 / 能干哪些活 | 从模板索引列 ID、模板名、文件、用途及常用组合，不背诵正文 |
| 剩下的概括 / 考考我 | 缩小展开范围，其余逐段标 `未讲解`；自测按需附 5～8 题 |

索引外对象借最近模板并注明范围，不按字段/报警另建模板。仅保留有证据且有帮助的章节，登记 `适用章节`；缺资料交可确认部分、列最小追问。

### 默认逐段版式（与选择器同源）

局部讲解与长手册各逻辑段默认采用简约五部分模板；写作去重遵循 `local-code-explanation.md` 的“简洁写作提示词”，长手册装配遵循 `handbook-guide.md`。模板只规定结构与表达，不代表程序语义或运行验证通过；用户当次要求优先。

详细代码讲解与完整手册默认采用 B 版逐逻辑段五部分：每个完整逻辑段都前置六列关键变量表，按功能定位与执行条件 → 源码 → 代码块整体讲解（处理过程、关键逻辑、写法好处、状态变化）→ 形象示例 → 程序交互与段间交接展开，并保留批判性审查与验证状态。每段完成具体示例和交接后再进入下一段源码，不能整节贴码后只共用一组示例或只对代表段使用该格式。标题固定语义表情，层级统一，源码与表格之间单空行；章→模块→逻辑段→五部分，四字段用独立加粗行。用户已要求完整范围就连续覆盖所有可读段并最终合并 Markdown，不等待逐段确认。大型嵌套结构先界定外层边界再讲语义子段，标明尚未闭合的承接，不能截断表达式或原注释；短闭合逻辑不硬拆。短事实问答、原样归档及当次明确只要摘要除外。源码覆盖、逐段栏目和教学语义分别核验。

### 四字段必须落到源码事实与第一性因果

处理过程、关键逻辑、写法好处和状态变化都从实际源码、声明、已知需求及工程连接推导，不能用栏目套话凑数。处理过程点名输入/前值→入口与分支→写入/未写→后值；关键逻辑保持其它输入及前值不变，用改变或去掉一个条件的具体反例解释它约束哪条路径、在已知目标下解决什么问题；写法好处按具体结构→可核对的行为差异→局部收益→代价/边界，不凭代码存在断言必要、最优、安全、高效或作者意图，无比较依据即说明不足以确认优势；状态变化核对全部可见写点、保持和后写覆盖，并注明观察位置。需求未知时只确认实际行为，可能目的标推断，不能虚构现场事实、扫描周期或平台语义。第一性原理融进每段正文，不另立方法论标题。完整手册在逐段分析前还须提供可追溯的整机逻辑路线：输入→入口条件→状态→输出→消费者→复位；未知调用顺序须明示，不按节号猜流程。语言按讲师带读方式组织：先说本段作用，再讲条件与结果；短句、一句一个因果，术语先白话解释；删重复背景和空泛评价，但不删条件、顺序、写入/保持及边界。删除变量名后仍能原封不动套到其它代码的空泛句，应回到具体条件、写点和数值反例重写。

**注释前置参考**：B局部讲解、C长手册及D教学重建每次写注释前，必须按 `inline-comment-style.md` 的“注释前置参考”加载该文件和 `inline-comment-examples.md`，包括命名辅助推断；已有有效上下文可复用，压缩或独立请求按该节恢复参考。默认采用简洁业务短注释，不把推断当声明事实；用户要求原样源码时不追加。

## 取证、清点与讲解步骤

1. **判输入与边界**：核实平台、版本、文本可读性和证据范围；工程材料先按 `workflows/read-project.md` 识别品牌、产品线、格式和版本，再从厂商入口加载匹配的解析经验；无经验则只读核实或请求最小替代导出，不假定 XML 一定含源码。
2. **清点与建图**：按该厂商格式实际的工程树/程序组织恢复对象归属，依据真实引用映射源码、声明与配置，再追调用/读写；`Tasks → POU → Sections` 仅是可能层级，不强套其它平台。完整范围清点全部，局部只恢复目标所需证据，片段和截图不建整机地图。工程树排列不证明执行顺序；输出与对象选择仍按原路由。
3. **选模板与深度**：按上方选择器及 Quick Start 加载；完整手册按 HBK → 对象 → 专题组合，多册另建总览索引，不把深度路线当普通默认。
4. **按依赖讲解**：代码均遵循选择器推导路径；复杂框架学习按 `workflow.md` 的分阶段路线，从执行框架与调用证据开始，经代表工位完整周期、第二工位对比，扩展到全部可读模块及段间逻辑关系、异常与恢复，最后整理学习手册；可按用户问题跳转，不把推定关系写成事实。教学重建另按其专用路线；局部深讲按 B 专用路线。前置证据不足只列最小缺口，不排日/周课表；三层结构、五部分与版式见 `handbook-guide.md`。
5. **校验与交付**：事实回答给可核验直接答复；B 按局部参考核对完整原码、五部分与适用语义，检查状态诚实。仅在有工具且实际做产物校验时，读取 `workflow.md` 的“局部产物校验”一个区段；普通讲解不读 workflow 全文、不做 Git 或维护回归，也不为标记细节先读脚本源码。无工具记未执行；未知工程事实或语义待审可标明后交付成品，不冒称检查通过或验收完成。完整手册、教学重建和源码归档才按对应入口运行适用检查并交付 `.md` 文件。多册用索引联接；分批与完成见 `workflow.md` 的适用区段。

## 领域细则

- **PLC-SAFE-READONLY**：始终只读；受保护 FB/FC 计入未覆盖，失败即停，不推测内部行为。安全边界以模板索引为准，处理流程见 workflow。
- **PLC-EVIDENCE-LEVELS**：关键结论用 `已确认`、`推断`、`未知`、`不适用`；已确认须给依据位置，不编变量、网络号、机械动作或维修结论，地址含义只来自符号表。规范见 `structure-mapping.md`。
- **PLC-FB-STATE（FB 保持语义分层，硬性）**：把“保持”拆三层讲，禁止用一句“未知/纸面假设”笼统带过。①**同一实例的调用之间**输出与内部变量保持，是有状态 FB 的**语言语义**（TwinCAT 3 Object Function block：“The values of the output variables and the internal variables are retained until the next execution.”），纸面推演的跨调用前值承接以此为前提成立，不必降格为假设；②**首次初值/首次调用前后**由实例声明与平台初始化策略决定，未见即未知；③**掉电、下载、RETAIN/持久化**未给资料即未知。任务周期、是否真被周期调用、并发或外部写者三者独立属未知，必须各自标注。方向错误同样禁止：不能因②③未知就把①也写成未知（读者的因果推演随之失去支点），也不能凭①去断言未提供的任务调度或扫描周期。
- **PLC-SEGMENT-DELIVERY（分段交付，硬性）**：长任务先自动清点所有可读对象/代码段，生成固定编号与顺序的完整覆盖清单，再自动分段并按完整逻辑结构组织批次；每批只写一个逻辑单元或一个完整模块，源码闭合结构不得截断。连续完成全部批次，不等待用户逐段回复“继续”，除非用户明确要求暂停/逐批确认。每批保留稳定术语与编号，并更新已完成范围、未完成范围及下一批起点；不得因代表性示例或篇幅限制把其余可读代码省略。若受单条消息或上下文上限影响，明确记录断点并自动从断点续写，不把技术限制伪装成用户确认。单批正文按平台安全长度控制；超限时在完整段落/模块边界拆批，代码围栏必须完整。全部完成后按原编号合并、核对覆盖清单、统一术语和链接，再交付最终 Markdown；不能以聊天中分批发过代替最终成品。**长文逐段质量验收**：覆盖与源码对账不等于讲解完成；每个可执行单元须解释条件真假路径、关键变量、写入/不写和保持边界，提供适用的连续状态推演及单因素反例；语义未通过/待审的单元不能标记为已讲解，覆盖与讲解质量分开计数，细则见 `workflow.md`。
- **PLC-KEY-VAR-TYPES（变量类型，硬性）**：关键变量表必须含「数据类型」列，数组写下标范围与元素类型，结构体写到使用的成员层；声明未见时数据类型列写 `未知`；允许结合前缀、英文词段、作者注释与读写上下文推测用途或命名约定，明确标为 `推断`，不得当作已确认的类型、作用域、接口方向或物理动作。具体方法见 `inline-comment-style.md` 的“变量命名辅助推断”。类型影响结论时必须点明溢出、比较不一致等后果。
- **PLC-LAYOUT-PLAIN（布局与通俗，硬性）**：模块编号方案在文首声明且全文统一；章 `##` 只放工程级内容，单对象模块 `###`、模块内小节 `####`；多工位时工位 `###`、模块 `####`、模块内小节 `#####`；模块内顺序固定为“一句话说清 → 功能定位与执行条件 → 源码 → 代码块整体讲解 → 形象示例 → 程序交互与段间交接”。每个模块开头必须有一句不含变量名与 `IF/CASE` 的**一句话说清**，术语首次出现给白话解释，关键逻辑先讲人话结论再给代码依据。细则见 `handbook-guide.md`。
- **PLC-ST-LAYERS**（完整手册或明确深讲）：ST 必须“总框架 → 大框架 → 小框架 → 逐段精讲”；一个大框架未讲完整不得切换到下一个。分层与代码块切分见 `code-reading.md`。
- **PLC-BLOCK-GRANULARITY（大闭合结构分块，硬性）**：单个 `IF/ELSIF/CASE/FOR/WHILE` 内含多个逻辑子块、整段贴出超出可读长度时，按“外层骨架 → 内部子块逐段 → 整体汇总”三层讲。先给该结构完整起止范围与整体入口条件；骨架仅用围栏外的行范围导航，列完整起止、分支锚点和尾部位置，不复制头尾源码或用省略号填源码围栏；真正源码在第二部分按原顺序完整保留一次。再按内部语义单元（条件组、赋值组、状态更新组、循环体的一步）逐段贴码讲解，每段说清触发条件、读写目标、本次写入/不写，以及对同结构后续分支的影响。全部子块讲完后必须补一次整体汇总：执行顺序、分支互斥或优先级、完整状态变化。子块边界取闭合结构或语义单元，不切断表达式、单条赋值和原注释；禁止用省略号或“其余同上”代替源码，禁止让读者以为结构被截断，也禁止跳过某子块直接进入下一个外层结构。
- **PLC-COMMENT-DEFAULT（默认逐行业务短注释，硬性）**：B局部与长手册的 ST/SCL 等行式源码**默认逐行**追加业务短注释，不需要用户再次提出“逐行”。每条执行行、条件行、跨行判据、调用行与结构行都在完整原行之后写 ` // AI: `，说明对象、动作与结果，必要时加条件；`IF`/`ELSIF`/`ELSE` 与跨行条件必须交代检查对象、判据与选路，不能只注释分支内赋值。只有空白行、纯注释行和块注释内部行不补；原有作者注释逐字符保留，新增说明一律追加在其后，同一行不叠加第二个标记。LAD/FBD 按网络或图元级说明，不改写成逐行 ST，也不运行 ST 专用 CLI。先加载 `inline-comment-style.md` 与自造示例；用途依赖命名推断时标“推测”，类型、方向、作用域遵从声明；不把请求、记录或变量置位说成设备物理动作已完成。**不得以“信息量不足”“正文已讲”“精简版”“避免重复”为由省略应有尾注——注得不好就改写，不能靠删注释通过门禁。** 仅当用户当次明确要求原样源码或仅归档时，才交无新增注释的原码，并在交付说明中写明该模式。校验见 `scripts/check_plc_comments.py`（默认为逐行模式，`--original-source` 才是原样源码）。
- **PLC-TEMPLATE-ADDITIVE（模板只增不删，硬性）**：要求在指定模板上增补目录、分章、模块编号或源码分块时，交付是**在原模板上叠加**：原栏目名称与顺序、变量表、整体讲解四字段、审查与验证状态逐字保留，新增导航放外层或作为可选槽位。不得以“新版式更清楚”“合并更紧凑”为由改名、合并或删掉原栏目，也不得把原模板重写成另一套骨架。交付前逐条对账原模板的每条非标题正文仍在新模板中（被用户批准替换的句子单独列出），并核对源码块剥离本轮新增尾注后拼回与原码逐字符一致；对账只证明源码在，不证明教学栏目还在，两者分别计数。明确要求恢复指定原模板时，按指定提交还原全部改动文件，报 `git status` 干净、`HEAD` 未变、逐文件哈希与基线一致，并把中间版本留在仓库外的备份目录，不留在工作树里。
- **PLC-COMMENT-PRECEDENCE（注释规则优先级）**：当次明确要求优先于默认设置；采用的模板须与当次要求一致，冲突时先明确适用口径。默认逐行追加注释，仅在当次明确要求原样源码或仅归档时不追加；不得自行降为选择性注释或“有信息才注”。LAD/FBD 按网络或图元逐项讲解，不将图形改写成逐行 ST。
  - 原注释先核实再借鉴，区分请求/反馈/记录与真实机械动作，原码及原注释保真。
  - 主要改注释就只改尾注和对应候选规则，不重写正文/栏目；先用少量真实源行校准表达再批量回填，不以覆盖率和审查条数证明阅读质量。
  - 模板来源限定到特定分支时，按 `skill-maintenance.md` 的“模板来源与注释风格迁移”仅核对来源；风格迁移与扩样仅在相应维护任务中加载。
- **PLC-CODE-SOURCE**：保留源码、变量名、网络号；ST 原样，LAD/FBD 不改写成伪 ST。语言按**单元**判定（一个 network/rung、一个 ST 文本块各算一个单元），混排时先给“代码单元清点表”再给综合结论，禁止用单一语言标签概括整份文档；判不出就写未知。注释只追加、不改源字符，代码块标 `<!-- src: -->`；未知行号用 `none` 并说明，注释版不声称可直接运行。
- **PLC-COMMENT-VALUE**（注释价值门禁）：**默认即逐行**——每条非空代码行都要有非空 ` // AI: ` 尾注，只豁免空白行、纯注释行与块注释内部行；覆盖率是底线而不是成绩。套话、重复粘贴、字段直译、只有“执行赋值”“条件判断”等无对象说明仍算错误，所以不得为凑覆盖率交低价值注释，也**不得靠删注释通过门禁**。用户当次明确要求原样源码或仅归档时用 `--original-source`，该模式不要求新增注释；`--legacy-selective` 只用于复核历史选择性注释夹具，日常交付不得使用。空白和纯注释行不重复补注，清楚的原注释保留，新增内容只追加在完整源行之后。普通局部 B 默认保留完整原字符与原注释，并逐行追加业务短尾注；五部分正文不改成独立逐行表。词法、质量与语义审查见 `comment-quality.md`。
- **PLC-TITLE-EMOJI（表情，硬性）**：**章标题、模块标题、模块内小节标题都要带表情**（不只是模块标题），关键提示（易混淆点、注意、缺口、危险动作）同样带；模式 B 按局部参考的语义表情方案丰富标题与提示；完整手册/教学重建同类内容固定同一组（章 🏭、模块 🔍、小节 🔹、示例 🧪、缺口 ⚠️、交互 🔗）。整篇只有零星表情也算未达标。整篇无表情按**版式缺陷**处理，不得以"表情非强制"省略；代码、变量名、表格字段、证据等级内禁放，表情不替代结论。细则见 `handbook-guide.md`。
- **PLC-DELIVERY-FORM（交付形态，硬性）**：详细讲解、单模块深讲、完整手册**最终必须合并成 `.md` 文件**并回报绝对路径。长文本按工作流先在聊天中自动分段、连续完成全部范围，再合并为一个 Markdown 文件；只有用户明确要求暂停/逐批确认时才等待。短局部详细讲解可直接写文件；只有用户明确要求纯聊天答复时才不建最终文件。**附件交付请求直接投递成品 `.md`**（`MEDIA:/绝对路径`），只配两三行：这是什么版本、已纠正/已验证什么、哪些未验证；不在附件前后复述进度、不重贴正文、不再问「要不要发」，也不以摘要代替原件。投递前用 SHA-256 与交付记录里登记的值比对，确认发的是修订后的那一份而不是首轮稿。
- **PLC-TEMPLATE-COMPOSE**：ID/版本/组合的唯一来源为模板索引，输出记录所用 ID/版本；共享字段和同一源码不重复定义。示例只示范结构，不能作为用户工程事实。
- **PLC-DELIVERY-VERIFY**（完整手册）：关键变量前置；模块严格采用五部分块级顺序“功能定位与执行条件 → 源码 → 代码块整体讲解 → 形象示例 → 程序交互与段间交接”。类比可省略且须限界，关系保留来源/目标、时机、丢失后果。见 `handbook-guide.md`。

  **讲解质量底线**（生成后自查 `quality-checklist.md`）：处理过程写清输入→判断→结果；关键逻辑从事实与约束推导所需行为，以单因素删改反例核对；**按读者卡点选一种思维方式贴着实码展开，不堆方法名**——问“为什么需要这个条件”用第一性原理（目标/已知事实与约束→条件的必要性→删改后果），跨模块影响用系统交接（输入→状态记忆→输出→消费者/反馈/复位），同次调用与下次调用分不清用正向时间线，从某个结果倒查原因用反向追因（先枚举该值在可见范围内的全部写点再逆推条件），要验证某个输入是否改变结论用单因素对照，要判断某值能否产生/清除用不变量与可达性，嵌套过深用分解再重组；方法要融进因果说明，正文不设“本节使用 X 思维”的方法论小节，方法名只在确实有助于定位时出现，不得以方法论代替条件与值的推演；写法好处只写有证据的局部收益和代价，不能确认比较优势时如实说明。

  状态变化区分本次写入、不写与跨调用保持（保持按 PLC-FB-STATE 三层写，不一律写未知）；**`CASE` 选路时机两侧都要讲**：分支体内的状态赋值不会触发 `CASE` 第二次选路，但 `CASE` **之前**执行的状态复位/夹紧（如 `Reset` 先把 `State:=0`）会被同一次调用的选路看见，因此“复位”与“再起步”可能在同一扫描内依次完成（如 `90→0→10`），推演不得写成“复位只影响下一次调用”；在给定调用集内确实不可达任何写入路径时，写“本资料范围内无清除路径”并写明前提，而不是一边断言锁存一边把语义写成未知；真正未提供的（外部写者、任务调度、重初始化）才写未知，不补造复位方。

  示例用真实变量、具体初值、至少3次连续执行，逐步核对分支、前后值和时间；无调用证据不冒称每扫描执行。连接词、字数、栏目齐全均不证明因果正确。
- **PLC-SOURCE-DEEP-TEACHING**（真实源码新手手册）：逐代码块覆盖现场动作、进入/退出条件、块级因果、跨扫描变化、易误解/执行顺序/多处写入、下游交接，并给调用链与运行边界；可读却省略的行按未讲解计，禁止截短条件、目标或分支。六槽位与合并说明边界见 `teaching-from-scratch.md`。
- **PLC-ORDER-SCOPE**：归档节序不证明调用顺序；跨节下扫描消费仅作条件推断（同实例、按此顺序调用），列待查 Task/POU/实例证据。单分支范围比较（如车号 1..128）非全局下标保护；逐读写点核实越界，AND 先后不证明短路。**范围条件必须四件事齐讲**：①点名它约束的是哪个量——该分支读出的索引/编号本身，而不是同处出现的工位号、循环计数器一类邻近量（写成「判断车号」而不说清约束对象，读者会套到错误的变量上）；②写明端点是否包含（闭区间要能一眼看出最小值和最大值都可通过）；③说明这一比较在保护哪一次访问或哪一条分支，拿掉后会取到什么越界值、走哪条路径；④限定作用范围只到本分支，不得引申成「程序已做越界保护」。示例须把边界走一遍：下界、上界、紧邻的越界值各一次，只演中间值不算验证边界。
- 保持源码覆盖清单、模块锚点和编号稳定；不写“其余略”。已识别 ≠ 已讲解 ≠ 已理解；缺资料或受保护只能称部分覆盖，多处写入须先核实扫描顺序，不能直接判“双线圈错误”。**写点清单先扫全档再落笔**：变量表“谁写谁读”格、交接表的置位/撤销行要写某成员的写点时，先用脚本按成员名＋赋值号扫全档源码，逐处记「节号＋行号」并区分 TRUE／FALSE，再据此成句；只写当前块看到的那一处，或沿用上一稿的行号，会把别节的清除点漏成“本资料没有复位”、把旧行号写成不存在的写点。

## 审阅、精简与成果保护


**审查意见先复核再改稿。** 审查报告本身会出错，不能当成事实照改。收到对讲解稿、模板或检查器的批评时，逐条回源码定位证据，标为合理／部分合理／不合理／证据不足，只改前两类，后两类在报告里写出反驳位置和依据。已知的出错形态：把同名或相邻的定时器实例数错（一个 `Tonx` 调用说成两个 TON）、把 `IF/ELSIF` 说成 `CASE`、后一轮审查把前一轮未经核实的结论当既定事实沿用、批判审查引用的行范围实际包含赋值行而结论正相反、把一处看似「两个变量混用」的示例判成算错，而更上游有一句把其中一个输入复制给另一个变量（两变量同源，示例本身成立）。所以引用任何行区间前先打开那几行确认里面真是它声称的写法，并向上追一层「谁给这两个变量赋值」再判是否混淆；同一批被指出的问题里既有真错误也有误判时，分组交付而不是整批接受或整批驳回。派发改稿时把裁定为「不合理／证据不足」的条目写成「不要改」并附理由，否则实施方会把误判当缺陷一起修掉；修订另存新稿、保留被审原稿，否则报告引用的行号失去对照。

**审查回报「声明类别未知」时先查声明段，别顺着它在稿里写未知。** 变量表已把某符号列在 `VAR（内部变量）` 下、只是序号列写 `-`，类别就是已确认；把「表里没给序号」读成「声明类别未知」，会让整段跨调用保持的因果被降格成纸面假设，反而与 PLC-FB-STATE 第一层冲突。收到「待补证：声明类别／`VAR` 还是 `VAR_TEMP`」这类条目，先回源码的 `VAR`/`VAR_TEMP` 列表与变量表定位该符号：能定位就改判已确认并重写受影响的句子（首次初值、重初始化、外部写者仍可未知），两处都没有才保留未知。审查给的行号与跨节引用同样要自己打开那几行确认——把 `THEN` 行当成赋值行、把写点指到「后文」而不是具体节与行，是这类报告的常见偏移。

**审校产物单独落目录，机械对账过了才谈语义。** 审校稿写 `reviewed-fields/<单元>.json`，不覆盖 `state/fields/` 里的原生成稿（原稿是行号与差异的对照基线）。固定四步验收：顶层键集合相等 → `annotations` 行号键集合相等（键集不等说明审校顺手增删了尾注）→ 用技能自带 `render()` 重新渲染通过 → 再跑 `validate_handbook.py`。四项全绿只证明结构与源码对账，语义仍要逐条回源；`// AI: AI: …` 这类前缀叠加是批量生成与审校两轮叠加的常见残留，渲染后对新增尾注 grep 一遍双前缀。

**讲解稿的语言/教学审查：交审查，不交改写。** 仅要求审查既有手册的语言、逻辑、通俗性、因果推导与注释价值时，交付物是一份只读审查报告，**不重新生成稿子、不顺便改注释、不把结构/保真校验通过当成教学合格**。逐行要落在三层：正文每个非空语义行归入一个段落单元并各自给判定、每个可读源行一条判定（解释充分／需补讲／无需重复／待资料）、每条新增尾注单独做删除测试；几百行共用一句理由等于没查。

源行判定必须带「正文解释位置」字段并指向具体正文行：没有新增尾注不等于没讲，把无尾注的行一律判「需补讲」而解释位置留空，是这类审查最典型的假阳性——判「需补讲」前先读该行所在块的正文。尾注删除测试要读完整个句子：前半句有信息、后半句指代含混（「未知的初值」指哪个变量）应判「改写」而非「保留」，整批复述「均有用」同样是没查。

问题分三类——**讲错（与源码矛盾）、讲得不清楚（读者会卡住）、风格偏好**——每类给原句、卡点、可粘贴改写示例的取舍；同时写明哪些段已经满足要求，使审查同时覆盖符合项与缺陷。生动不能靠堆比喻或表情：形象示例必须用真实变量、具体前值、走的分支和落到的写入，类比把「请求」写成「动作」、把「记录」当成「事件」就是讲错了。第一性原理看是否推出条件与写点的必要性、改一个条件会怎样，不看到出现「第一性原理」四个字（与「讲解质量底线」同一口径）。

语言审查与语义审查分两个互不可见的只读轮次，先读对方结论再评会让同一处错误被两轮一起继承；派发前冻结稿件 SHA-256，审查后重算，证明原稿未被改动。

**讲解稿的精简修订：删重复，不删因果。** 要求提升既有稿件的清晰度、逻辑、通俗性与规范性时，这是对**稿件本身**的可读性要求，不是要更短的摘要：五部分骨架、关键变量前置、读写/保持/覆盖/后写先后、证据边界全部照旧。逐句做删除测试——删掉后读者会丢掉条件、来源、先后、本次写入或不写、边界理解才保留。首删项是同一结论在“一句话说清/功能定位/整体讲解”各写一遍、重复的免责声明、“本节逐段……”式元话术、把源码顺序再抄一遍的流水账。

全局变量表的“谁写谁读”格只列真实访问的模块与行号（模块编号与已核验行号），把“未列模块＝本片段未见”“外部写者未知”“结构成员另缺”提到表头说一次，不要每行复述全部模块名加同一句未知，避免大量重复说明淹没真实读写证据。**成功标准是读者能复述，不是字数下降。** 修订后仍不清楚时，重新核对正文因果与阅读路径，逐模块改写讲解，不以表格或字节统计替代正文改进。

每块先一句白话“这块做什么、什么时候执行”，再按源码实际顺序讲条件→动作→本次写入/不写→结果，删掉免责声明和“本节将逐段……”式元话术，只留一个能跟着数值走的示例。**大体量全局变量表移出主线**：大规模逐点读写清单放到文末“查阅附录：变量与源码索引”，保留六列与行号证据；模块源码前只留该模块讲清逻辑必需的 3～10 个变量，表头统一交代“未列模块＝本片段未见／外部写者未知／成员定义缺失”，不在每行复述。

验收逐模块问一句“第一次学的人能否复述输入→条件→写入→结果”，答不能就继续改那一段。委派外部执行器重写或精简时，先比对正文段落是否真的重写，再看报告与统计：只改统计、表格或目录的交付按未完成退回，不因报告写着“已验证”就放行。压缩后复核每个关键分支仍有具体前值→条件→写入→结果，示例不能退化成机制复述；用户要的是更好读，不是更少内容。

**参考经授权的既有成品。** 需要借鉴既有讲解的教学组织方式时，只在用户指定或已授权的资料位置寻找既有讲解，分析它如何介绍设备对象、符号、实例与调用，再组织导航、分段判断、赋值结果和模块联系。观察其数值示例、短轨迹表和停顿提问的组织方式，只迁移写作方法；不把私有路径、原文、工程结构、实现代码或设备特征写入技能资产。与本次源码无关的章节和练习不照搬，现场行为仍按证据确认；未找到可参考成品时说明依据。讲解仍难以理解时，重新安排概念引入和阅读顺序，不能只继续缩短文字。

**模板可读性修订保留既有栏目。** 模板本身存在可读性问题时，先调整阅读路径与说明方式，不用增加栏目、表格或术语代替改进；未审阅样稿前不替换已安装模板。交付候选模板与代码试讲样稿两份独立 `.md`，确认后再接入。**指定模板 `.md` 是当前任务的唯一定义**，模板资产、生成规则与校验要求须保持一致，并通过实际生成的测试稿验证。明确区分模板机制修订与单份稿件修订，按获准范围执行。



**进程退出码 0 不是产出证据。** 生成/审查的包装脚本常在服务端无可用账号、返回空结果时仍 exit 0；判定「已审查」前必须断言记录条数与键集，例如已生成注释键集合 == 审查记录键集合、`completed == total`。只有进度文件与原始响应都在、条数对得上，才算这一轮产出成立；空结果、失败轮次照实记进报告，不能因为脚本没报错就并入「通过」。源码保真另用独立副本对账：从归档原文重新切片与样稿逐字符比较，不用生成器对自身计划的清单自校验。细则见 `reader-first-progression.md` 的“用户交来自己的模板稿时”。骨架固定为“真实问题开场 → 带着问题读源码 → 条件分组为门 → 连续执行轨迹（须含条件回落而输出保持旧值的那一次）→ 单因素对照 → 双向反查 → 抛问题给下一段 → 查阅层后置”；方法名融进因果说明，不各占栏目。源码保真、纸面模型断言与归档哈希口径见 `reader-first-progression.md`。


完整手册须有可核验的来源与源码覆盖；具备匹配源码与清单时，缺失/重复/多余/改写/截断/归属六项全 0、覆盖率 100% 才称完整。**覆盖率以独立源文件对账为准，不以生成器对自身计划清单的自校验为准**：计划漏行时自校验仍报满覆盖，须逐节核对源码逐字符相等与单元起点连续，见 `handbook-build-toolchain.md`。受保护或缺资料只能称部分覆盖；静态通过不替代语义审查。B 以剥离本轮新增尾注后还原为原码逐字符一致为准，计数与末行核对不能证明相同；原注释触发安全扫描时如实区分源内残留与新增，不改源刷绿。

**修订指定历史成品前先确认来源**：要求恢复指定既有格式时，先把用户指名的版本对应到实际文件——查本机归档目录、CHANGELOG、Git 标签与对象；标签缺失不等于成品不存在，找不到该版本就找同结构的现存成品，并如实说明依据的是哪份文件而不是凭记忆复原。偏离诊断要落到具体项（编号体系被换成验收/质检编号、模块被并成章节、字段槽位被合并或新增第六部分、源码被摘要替代），再按该成品的骨架重做，不按当前校验器或当前测试稿的形态重做。仅要求从指定版本删除某项时，这是对**那一份文件**的外科删除，不是按当前 skill 重新生成：以指名版本为底稿只删目标小节（连目录/元信息里对该小节的计数一并改），再用差异证明改动范围——源码围栏与底稿逐字符一致、目标小节计数为 0、其余正文除被删块外无改动；底稿本身触发的校验失败如实归因到原稿，不把删除前的既有问题说成这次引入。各模式的产物校验操作见 `workflow.md` 的对应区段，检查结果按实报告。

教学重建须有每阶段实例、周期调用和模拟输入，多模块须覆盖所有权、请求≠确认、逐扫描反例与恢复闭环；依 `teaching-from-scratch.md` 盲走审查后再交付。无目标平台证据只称参考实现/未验证，`部分满足` 按未完成处理。未要求深讲的 A 不加载完整审查门槛；B 仍须按局部参考核对源码、版式与适用语义，未运行不报通过；局部深讲使用适用教学检查，不扩成全项目审计。

完整手册、教学重建和源码归档的 `.md` 开头均写 `工程：` 与 `讲解深度：`；归档填 `归档（不讲解）`。输出保留基线版本的章节表情，精简结构时不要一并删掉。**每个模块标题必须带表情**，正文关键提示可带表情；代码、变量名、表格字段与证据等级内不放，表情不替代结论；标题不跳级，表格列数一致。大型手册的生成器与收敛次序见 `handbook-build-toolchain.md`。

**正式稿件边界**：成品第一行是独立的 H1 标题，其后直接呈现对象/范围、关键变量和所选模式正文；交付消息另写执行进度与修改说明。代码讲解正文只含当前教学内容、来源、假设和未知，保持与聊天回应、修改过程及维护记录分离。
