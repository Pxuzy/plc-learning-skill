# 决策 001：保留宿主入口，以局部委托接入项目门禁

状态：已批准的第一阶段准备实施选择；等待用户检查工程树，随后才做自我审查验收。它只裁决本轮门禁接入，不批准提交或发布。

原计划比较了两种选择，并有条件建议仓库分派器。本轮任务明确优先使用现有宿主的 `privacy.originalHooksPath` 契约，因此选择最小局部委托：保留继承或既有 `core.hooksPath`，仅将当前仓库的 `privacy.originalHooksPath` 指向版本化 `.githooks`。宿主先扫描，再委托 pre-commit；commit-msg 先执行宿主格式/隐私检查，再委托项目规则。其他阶段仍由原宿主处理，不引入通用转发包装器。

| 方案 | 优点 | 代价与裁决 |
|---|---|---|
| 宿主入口 + 局部委托 | 不替换任何宿主阶段、参数、stdin 或退出路径；只拥有一个局部设置 | 宿主会跳过缺失/不可执行委托，doctor 必须检测；本轮采用 |
| 仓库入口 + 完整分派器 | 项目可在每次调用前验证宿主存在 | 须完整转发所有现有宿主阶段、stdin、参数、退出码并防递归，维护面扩大；本轮不实施 |
| 无宿主的 local-only | 可独立使用项目政策 | 仅显式选择且确认无任何既有宿主/默认有效 hooks 时允许；不冒充有宿主保护 |

安装器只支持已经核对的 privacy adapter 形态，固定关键脚本及依赖文件哈希到非版本化本地状态；doctor 检查依赖、执行权限、有效配置、回环与宿主漂移。未知宿主、已有委托或有效默认 hooks 均拒绝覆盖；需要另做链设计，不能静默切换 local-only。宿主绝对路径只由现场发现并存于本地状态，不写入版本文件。

边界：doctor 的成功表示当时配置可达，不能保证 Git 在未来缺少委托时仍会调用仓库代码。宿主当前缺失/非执行委托会成功返回；删除项目 hooks 或修改局部配置可能让它静默跳过。实际 host 集成与 stub 合同测试分开：前者验证真实隔离提交与 Git hook 跟踪，后者注入宿主非零、回环、参数/stdin 和漂移。不会以 stub 宣称现场宿主已证明。

本地 Git hooks 可被 `--no-verify`、配置或手动改动绕过；如将来需要强制准入，应另行设计服务端门禁。本轮不增加自定义跳过变量，也不修改宿主脚本或全局配置。
