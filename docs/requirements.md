## 1. 项目目标

将现有 PLC 程序学习 Skill 规范化并改造成可长期维护的多品牌学习工具。它应能在证据充分时解析 PLC 工程结构、定位目标程序，结合源码、变量和调用关系，向 PLC 初学者产出真实、完整、清晰、可审阅的讲解，帮助读者理解局部代码和工程整体逻辑，并逐步学会自行分析。

## 2. 目标读者与教学原则

- 主要读者为 PLC 初学者；以规范工程语言为主，必要术语首次出现时简要解释，并用具体代码轨迹或执行例子辅助理解。避免过度口语化类比，不以牺牲技术精度换取“通俗”。
- 讲解不止翻译语句；要说明代码块负责什么、解决什么问题、关键输入/状态如何产生结果，以及它与周边程序的已知关系。
- 在证据允许时，适当运用第一性原理、逆向推演、系统思维和边界反例，带读者从控制目标与约束、输出与故障、程序/变量/状态之间的联系来理解代码。
- 思维方法是解释和学习工具，不是补造作者意图、业务需求或缺失架构的许可。结论必须能回指工程树、声明、注释、调用关系或源码；无法证实时标注“推断”或“未知”。
- 目标是让读者既能追踪局部执行过程，也能逐步建立整体架构与逻辑主线的理解。

### 2.1 需求分级与任务侧重点

为避免“核心目标”和“有帮助的扩展内容”被混成同等要求，所有需求按以下层级执行。任务开始时先识别用户要解决的问题和交付范围，再应用对应层级；不得为了补充项挤占核心分析时间或输出篇幅。

| 层级 | 定义 | 执行规则 |
|---|---|---|
| **P0 核心必需** | 缺失就无法保证讲解真实、完整、可用，或会直接偏离用户目标的要求 | 每项代码分析都执行；优先级最高，遇到篇幅、证据或工具限制时先保障这些要求 |
| **P1 条件必需** | 只在特定任务、输入或用户明确要求时成为必需 | 先判定触发条件；触发后按核心验收，不触发时不强加 |
| **P2 补充增强** | 有助于理解、迁移或扩展，但不是完成本次核心任务的前置条件 | 按相关性和证据选择性加入；不得重复核心内容，不得为“显得全面”而硬套 |
| **P3 后续治理** | 服务 Skill 架构、维护、发布或跨任务积累，不属于单次 PLC 程序讲解 | 仅在 Skill 改造/维护任务中处理；普通讲解不加载、不运行、不呈现 |

#### P0 核心必需：每项代码讲解均执行

1. **忠于可见源码与资料**：不改写原程序来代替讲解；不编造变量类型、调用者、调用顺序、扫描周期、设备动作、复位路径或作者意图。事实、推演、推断和未知清楚区分；证据不足时明确写未知及缺少什么证据。
2. **覆盖用户请求范围**：先界定输入来源和可读范围，覆盖范围内相关代码，不以摘要代替解释；资料不完整时准确说明已覆盖与未覆盖部分。
3. **解释真实执行因果**：对相关代码讲清条件/分支、执行顺序、关键读写、结果和状态变化；明确本次写入与未写入。块级说明代码承担的职责、解决的问题以及与其他代码的已知关系。
4. **逐行 AI 注释**：按用户已确认的要求，对教学副本中尽可能每条非空代码行加简短、准确的 `AI:` 注释，保留原注释；不可注释的例外说明原因，不回写 PLC 工程源码。
5. **可读且不误导**：代码按逻辑边界展示，避免一次倾倒过长代码；大型嵌套结构先讲完整外层范围，再分内部逻辑块讲，最后汇总执行顺序和状态关系；不因分块而遗漏请求范围。
6. **批判性审查不缺席**：讲解后检查可由现有证据支持的缺陷和风险；无可证实问题时说明审查范围，不能把“未发现”写成“程序完美”。
7. **交付诚实**：未运行的编译、仿真、静态检查或实机验证必须标为未执行；不得以结构格式通过冒充语义验证。

以上条款如遇证据缺口，合法结果是“未知/未验证 + 缺失证据”，而不是猜测填满栏目。短事实问答没有代码时，不强制套用逐行注释或完整审查章节。

#### P1 条件必需：仅在触发时执行

- **全局工程架构、调用关系与逻辑主线**：用户要求理解整体、完整工程或任务确实跨多个程序对象时，须基于工程树、调用证据、变量和状态关系建立全局图；局部问题不以整机地图为前置条件。
- **品牌适配与官方资料查证**：涉及具体品牌工程格式、I/O、事件、报警或 IDE 路径时，先定位品牌、产品线、格式及版本，再查相应证据；不得把一个品牌的术语或菜单套用到另一品牌。没有对应输入时，不为凑品牌覆盖而扩展。
- **执行轨迹与反例**：用户要求深讲/初学者教学，或代码涉及状态、时序、多个写入、边界条件时，给具体输入与状态轨迹；适当用单因素反例检查条件必要性。普通短答不强制复杂表格。
- **分段连续生成并合并文件**：长篇手册或跨模块交付时，分块连续完成并在全部完成后合并为单一 Markdown；短答不强制生成文件。
- **支持能力声明**：只有在实现/审计解析能力时，才按品牌、产品线、格式、版本和实际验证等级声明支持；讲解单个已提供文本片段无需先完成四品牌适配器。
- **安全影响评估**：仅当代码或用户问题涉及安全回路、危险输出、失效安全或人员/设备安全时，指出可见证据与缺口；任何情况下都不作安全认证。

#### P2 补充增强：相关时选用，不设为统一硬门槛

- **第一性原理、逆向推演、系统思维**：作为解释工具，从目标与约束、输入到输出、状态与故障反推逻辑；只用于澄清本次代码，不单独扩成理论课，也不推断作者真实意图。
- **跨模块系统视角**：用户关心总体结构时展示数据流、状态流、调用关系及模块交接；只对当前局部问题时，只补能解释该代码所必需的上下游证据。
- **更丰富的示例、边界反例、对比实现**：按学习难点选择，必须标出假设和适用边界；没有对照实现时不编造“写法优势”比较。
- **外部 Skill、厂商手册与社区资料调研**：用于补充依据或设计参考；与本次问题无关时不重复检索。外部资料不能代替实际工程证据。
- **更多品牌/文件格式、自动解析器、额外可视化图表**：作为后续能力建设候选；不应阻塞当前可凭源码完成的解释。

补充内容与核心解释冲突时，删除或缩短补充内容；篇幅不足时优先保留源码证据、执行因果、注释覆盖、未知边界及审查结论。

#### P3 后续治理：只在 Skill 改造或维护任务中执行

工程目录规划、Anthropic/Codex 规范兼容验证、仓库级 Git hooks、隐私扫描、语义化版本、提交格式、解析器与四品牌夹具、行为评测矩阵、分工及发布门槛均属于 P3。它们是 Skill 长期维护需求，不是每份 PLC 程序讲解的内容或门槛。只有进入相应 Skill 维护阶段时才按批准的方案执行，不因本需求文档列出这些事项而默认开始改造。

#### 单次任务的优先顺序

1. 用户本次明确要求和交付物范围。
2. P0 真实性、源码覆盖、执行因果、AI 行内注释、可读性、批判性审查和诚实报告。
3. 已触发的 P1 条件必需项。
4. 与学习目标直接相关的 P2 补充项。
5. P3 Skill 治理工作仅在用户明确进入该阶段后执行。

当要求冲突或资源不足时，先满足高优先级；范围或证据不足时缩小结论范围并标记未知，不以补充材料替代核心任务。

## 3. 多品牌工程识别与解析

### 3.1 首批品牌范围

首批规划西门子、欧姆龙、倍福、台达四类品牌适配器。每个品牌下的产品线、工程格式和版本范围分别登记；只有对具体组合完成验证后才可声明支持。品牌列入规划不等于其所有格式已实现或已验证。

### 3.2 处理流程

1. 识别厂商/平台线索、输入文件类型、工程版本及用户提供的范围；不能仅凭扩展名确认格式，不确定项标“未知”。
2. 检查现有解析工具及其对该格式的能力。可解析则按工程结构读取；无法或只能部分解析时，说明实际尝试、限制、未读取范围和需要用户提供的替代导出资料。
3. 恢复可见的工程树/程序组织结构，标出控制器、任务、程序单元（例如 POU）、函数块实例、程序段、数据类型、变量表等实际对象及层级；保留厂商原生术语，不强套统一名称。
4. 从用户指定的目标或问题沿工程树定位程序、代码块及源文件/对象路径，并保留可回查证据。
5. 在可见范围内追踪调用者、被调对象、公共逻辑、变量读写者和状态交接。没有工程证据时标“未知”，不从代码相邻或变量命名推断调用关系。
6. 对每种品牌、产品线、格式和版本独立登记解析能力、可提取信息、限制、样本/夹具与验证结果；未验证组合不得标为已支持。

### 3.3 重要输入证据

讲解程序时，优先收集并交叉核对：

- 工程树、任务及程序/POU/函数块调用关系；
- 数据类型定义、结构体/数组成员及相关平台类型资料；
- 全局变量表；
- 目标程序或 POU 的局部/内部变量表；
- 变量、符号及接口注释；
- 变量作用域、方向、初值/属性（可见时）、读写位置与实例关系。

- 对“IO 在哪里查、事件/报警在哪里看、变量如何追到设备”等问题，先识别品牌、系列、工程版本和目标对象，再按对应厂商官方手册/工程配置/IDE 交叉引用/运行时诊断来源查证。引用资料须标注适用系列、软件/固件版本及页节/URL；不能把一品牌菜单名称或工具位置套用于另一品牌。
- IO 追踪至少区分：程序符号/变量声明 → I/O 地址或过程映像 → 设备/模块/通道配置 → 方向与数据类型 → 程序读写点；每一跳都记录文件/对象路径与证据。事件追踪至少区分：事件产生代码/库 → 事件 ID/来源 → 记录/事件日志/报警配置 → HMI 或客户端呈现；没有相应项目配置或运行时记录时，不能断言事件已配置、已触发或显示在哪里。
- 支持按符号执行交叉引用/映射追踪，并报告未解析链接；在品牌资料中维护“对象术语—工程文件/IDE 位置—证据字段—版本范围—限制”的可查索引，而非只收录术语表。

### 3.4 外部 Skill 与官方资料调研

调研用于补充可验证的流程和厂商依据，不直接复制第三方 Skill，也不把社区材料当作厂商行为的最终依据。已检索并初审的参考：

- [MIGO-OvO/plc-skill](https://github.com/MIGO-OvO/plc-skill)：按通用 PLC 层和厂商专项路由拆分，并明确不同品牌覆盖深度不等；可借鉴渐进加载、支持范围声明和不确定时回退通用层。其仓库 README 列出多品牌，但当前仅作为社区样例，不据此宣称本 Skill 的适配已完成。
- [TwinCAT Mapping Reader Skill](https://github.com/Lance0901/2026-TwinCAT-Codex/blob/main/twincat-mapping-reader/SKILL.md)：按符号声明、`.tsproj` 的 `<Mappings>`/`OwnerA`/`OwnerB`/`Link`、任务侧字段、NC/设备/端子路径追踪；要求说明方向性、逐跳证据和未解析映射。可补充为倍福 IO/轴/设备映射专项工作流。
- [Siemens S7-1500 诊断概览](https://support.industry.siemens.com/cs/attachments/109752283/109752283_Diagnostic_Overview_DOC_V10_en.pdf)：区分集成系统诊断、用户程序诊断、Trace、错误 OB、在线诊断、HMI/报警等不同证据来源；可用于建立诊断问题的来源路由，需按型号/版本复核。
- [Omron Sysmac Studio 产品规格](https://www.ia.omron.com/products/family/3077/specification.html)：说明 Cross Reference 可列出变量、数据类型、I/O 端口、函数和函数块的使用位置；可用于欧姆龙符号引用与依赖追踪。实际功能需按 Sysmac Studio/控制器版本核对。
- [Beckhoff TwinCAT PLC 入门：GVL](https://infosys.beckhoff.com/content/1033/tc3_plc_intro/2530218891.html)、[IO 配置概览](https://infosys.beckhoff.com/content/1033/tc3_io_intro/1094759563.html)、[事件记录器介绍](https://infosys.beckhoff.com/content/1033/tceventlogger/12332564491.html)：可分别支撑 GVL、I/O 设备/过程映像/映射、事件来源与客户端呈现的术语和证据入口。
- [Delta 官方 PLC 下载中心](https://downloadcenter.deltaww.com/en-US/DownloadCenter?v=1&CID=06&itemID=060301)：列有 ISPSoft 用户手册、系列编程手册和模块手册；[Delta ISPSoft 产品说明](https://www.deltaww.com/en-US/products/PLC-Programmable-Logic-Controllers)说明 ISPSoft 集成硬件/网络配置并支持 IEC 61131-3。需求是先以该下载中心按 AH/AS/DVP 等具体系列与版本定位手册，再建立可验证的工程树、变量、I/O 与诊断索引；未核验手册细节前不宣称具体菜单或事件位置。
- 检索到 [Delta PLC Agent 工程](https://github.com/ufukefekaya-tr/delta-plc-agent)，摘要显示其覆盖 AX 项目、编译反馈与 ISPSoft/DVP 工具；它属于社区工具/Agent 工程，不等同于通用 PLC 教学 Skill。仅在检查其源文件、许可证、安全边界和可复核能力后，才决定借鉴具体实践。

### 3.5 第一版资料分类与建议工程树

#### 设计依据

本方案参考 Agent Skills 官方目录约定和成熟 Skill 仓库的分层实践：官方格式要求每个 Skill 至少有 `SKILL.md`，并建议用 `references/`、`scripts/`、`assets/` 按需存放文档、可执行工具和静态资源；较长资料按需加载，避免主入口承载全部细节。Anthropic 的公开 Skill 仓库按技能各自目录组织；PLC 社区 Skill 示例进一步把跨品牌知识、厂商资料、模板、样例、评测和维护指南分开，并区分厂商支持深度。

参考： [Agent Skills Specification](https://agentskills.io/specification)、[Anthropic Skills repository](https://github.com/anthropics/skills)、[OpenAI Skills guide](https://developers.openai.com/api/docs/guides/tools-skills)、[MIGO PLC Skill repository](https://github.com/MIGO-OvO/plc-skill)。OpenAI 旧 `openai/skills` 仓库已标记弃用，不以它作为当前目录规范的唯一依据。

│   │   ├── siemens/             # 西门子工程结构、术语、I/O、诊断等
│   │   ├── omron/               # 欧姆龙工程结构、术语、I/O、诊断等
│   │   ├── beckhoff/            # 倍福/TwinCAT 工程结构、映射、事件等
│   │   └── delta/               # 台达各产品系列与软件版本资料
│   ├── standards/               # IEC、Agent Skills 等规范的适用说明与链接
│   └── external/                # 外部 Skill、厂商手册、教程等参考线索及评估笔记
├── templates/                   # 不同讲解任务可复用的输出模板
├── scripts/                     # 工程盘点、格式解析、注释与文档检查等工具
├── evals/                       # Skill 行为、解析能力和讲解质量的回归用例
│   └── fixtures/                # 供回归测试使用的合成或获准脱敏样本
├── docs/                         # 维护和开发说明，不属于每次任务的运行时知识
│   ├── architecture/            # 工程结构、模块职责与资料流转说明
│   ├── decisions/               # 架构选择及其理由、影响和后续复核

以上只定义**文件夹及其职责**，不预先规定文件名、文件数量或每个品牌必须拆成几份。Skill 必需的入口、本体和平台元数据放在仓库根目录，不在这份文件夹树中展开。该结构是第一版建议，不是当前仓库现状，也尚未获用户批准；架构审计后按实际需要增删或合并文件夹，不为填满树创建空目录。

对外分发时，按目标 Skill 平台要求，从根目录本体及运行必需的参考、模板和工具中组装；维护文档、回归评测、测试夹具及仓库钩子默认留在开发仓库，不自动混入运行包。外部原始资料如有版权或授权限制，只保留允许分发的链接、书目信息和自有摘要，不复制原文。

#### 各文件夹的资料管理约定

| 文件夹 | 放什么 | 不放什么 |
|---|---|---|
| 根目录 | Skill 本体及平台要求的入口/元数据 | PLC 项目样本、临时研究笔记、运行结果 |
| `references/common/` | 与厂商无关的 PLC 基础知识、证据原则和通用分析方法 | 未经标注的单一厂商特例 |
| `references/workflows/` | 工程识别、解析、变量追踪、程序讲解和批判审查的按需流程资料 | 重复抄写到多个地方的硬规则 |
| `references/vendors/` | 按品牌和产品系列归档的术语、工程结构、变量/类型、I/O、事件/诊断与解析边界 | 没有来源或适用版本的“通用结论” |
| `references/standards/` | 适用规范的版本/链接、约束摘要及与 Skill 的对应关系 | 未经核验的第三方规范转述 |
| `references/external/` | 优秀 Skill、社区教程、厂商手册等外部参考的来源信息、可借鉴点、许可限制与评估结论 | 直接复制且无授权的第三方文件或大段原文 |
| `templates/` | 面向不同交付物的可复用结构骨架 | 与规范正文重复、互相冲突的规则副本 |
| `scripts/` | 确有重复执行价值且记录了依赖、支持范围与限制的工具 | 未使用的占位脚本或未经验证的“支持”实现 |
| `evals/` | 路由、解析、代码保真、AI 注释、讲解质量及批判审查的测试用例 | 用户真实工程或含隐私的原始项目资料 |
| `evals/fixtures/` | 最小化合成数据，或已获授权并脱敏的测试输入 | 未经授权的 PLC 原始归档、凭据、客户/设备标识 |
| `docs/` | 面向维护者的架构、决策和维护资料 | 运行时必须逐次加载的核心规则副本 |
| `.githooks/` | 仓库级提交格式及隐私检查入口 | 全局 Git 配置或会绕过宿主机保护的逻辑 |

所有外部参考与厂商知识都应能回溯来源、适用品牌/系列/版本、查阅时间、许可/分发边界和验证状态；证据不足标记“待验证”。具体讲解产物属于用户任务结果，不默认回写到知识资料目录；确需沉淀时，先去除项目特定信息，再以通用知识和证据来源形式整理。

品牌支持状态建议分为：`planned`（规划中）、`reference-only`（有资料索引，未验证解析）、`sample-verified`（指定格式样本验证）、`parser-verified`（解析器与回归夹具验证）、`runtime-verified`（指定 IDE/运行时验证）。对外声明必须限定到验证过的品牌、系列、格式和版本；不等于现场安全认证。目前四类品牌均按规划目标处理，不能据此宣称已支持。

### 3.6 对现有 PLC Skill 的借鉴与取舍

本节基于当前已安装 PLC Skill 的入口、references、模板索引、目录、工作流、质量清单、脚本与 evals 的只读检查。它总结可迁移的设计经验，不代表整套旧规范均适合新版本，也不授权直接改写或搬移旧文件。

#### 建议继承的做法

- **入口短、资料渐进加载**：旧 Skill 用入口选择任务范围，再按需读取专题 reference。新工程保留这一加载方式，把跨品牌知识和厂商资料分别放置，避免每次回答都加载全部品牌资料。
- **规则、呈现、检查职责分离**：旧 Skill 的 catalog 会把规则、模板、验证器和正反例联系起来；模板负责呈现，脚本检查确定性格式，人工审查语义。新版本可借鉴这种追溯方式，但采用更轻的目录登记，不照搬旧规则编号及长清单。
- **范围路由**：旧 Skill 区分事实短答、局部代码解释、完整手册和教学重建，局部问题不会被强迫扩成整机报告。新版本保留“按用户目标选择最小充分范围”的思路，针对新读者需求统一行内 AI 注释和批判审查的适用规则。
- **证据分级与未知边界**：旧 Skill 区分已确认、推断、未知、不适用，并要求声明来源、假设和覆盖范围；新版本应保留，并扩展到品牌、系列、工程格式、软件/固件版本和资料来源。
- **全局结构与局部因果并重**：旧 Skill 要求从任务/POU/工位/程序段和调用关系建立地图，再解释局部条件、读写、状态与交接。这与初学者建立全局理解的目标一致；仅在工程证据支持时呈现架构，不把教学路线当成真实调用顺序。
- **长文连续交付**：旧 Skill 会先清点可读范围、稳定编号、按完整逻辑结构分段，最终合并成单一 Markdown。新版本可继承覆盖清单、分批连续生成、完整后合并及源码保真核对。
- **教学质量与格式门禁分开**：旧质量清单把语义审查与格式检查分开，并强调代码轨迹、单因素反例、连续状态和未知证据。新版本应沿用这种分层，另加讲解后的批判性审查，不把格式全绿当作结论正确。
- **模板和样例承担不同职责**：旧模板索引有组合路由，示例文件展示完成产物；新版本可按讲解交付物保留“模板/样例”区分，但先从必要的少量结构开始，避免一开始建很多未使用模板。
- **测试使用合成且可追溯的 PLC 样例**：旧 Skill 有局部讲解与复杂 ST 的合成夹具及相应回归。新版本可用最小合成夹具验证格式识别、语义边界和反例；真实工程材料只有获准、脱敏后才进入测试集。

#### 不建议原样继承的部分

- **旧入口中的强定制版式**：旧 Skill 有五部分固定模块、标题表情、章节层级等契约。可将有帮助的模板作为可选交付形式评估，但不应无条件套给每个局部问题或新品牌格式；先用真实用户样例验证是否提升可读性。
- **旧品牌与产品专用实现**：现有欧姆龙 SMC2/XML 工作流是特定工程形态的经验，不代表西门子、倍福或台达的工程结构。应迁移“先清点、按原生结构解释、保留可见性边界”的方法，不能照搬文件解析假设或术语。
- **历史版本与迁移规则**：旧 Skill 的模板 ID、版本兼容、历史格式及大量重构维护约束是其演进产物；新 Skill 可在未来有多种稳定模板后再引入版本注册，不预先复制旧制度。
- **重复的硬规则与过度细化维护细节**：旧资料数量较多，存在为既有检查器、模型行为或历史故障服务的细则。新工程只保留当前仍适用且能说明原因、适用范围和验证方式的规则；其余不进入运行时入口。
- **旧版默认口径差异**：旧 Skill 对不同模式的原码呈现与行内注释有不同默认值。新需求已经明确教学副本尽可能逐行加 `AI:` 注释，不能直接复制旧默认；应按新需求统一，并明确何时输出原始源码、何时输出教学副本。

#### 迁移与验收原则

1. 先建立“旧资产职责 → 新目录类别 → 是否迁移 → 适用边界/待核验”的只读映射，不移动或删除现有资料。
2. 仅迁移能服务新目标的通用方法与有合法来源的厂商证据；旧示例中的程序事实不得当作新品牌规则。
3. 每一项拟继承规则配一个正例和一个反例；品牌事实另附来源、系列/版本、验证状态。
4. 用至少一个局部代码讲解和一个跨模块/工程地图任务验证：是否同时做到逐行 `AI:` 注释、块级原因讲解、整体逻辑说明、事实与推断区分及批判性审查。
5. 用户审阅并确认迁移映射及架构后，才进入实施；本节不是对旧 Skill 的重构授权。

## 4. 讲解真实性与深度及批判性审查
- 以用户提供的源码和可核实资料为事实依据，覆盖请求范围内所有可读代码；缺失/部分资料要列出覆盖边界，不把局部材料称作完整工程。
- 具体解释实际条件与分支优先级、变量读取与写入、本次不写、状态变化、保持/清除边界、执行顺序及可见的跨段交接；禁止空泛摘要、只翻译语法或只罗列变量。
- 每个代码块必须说明整体职责、所解决的问题、输入/状态到结果的控制过程，以及与前后代码的已知关系。逐行注释不能替代块级解释。
- 区分源码事实、明确假设下的纸面推演、推断和未知；注明未知所缺证据。不得虚构代码、调用者、调用顺序、任务周期、设备动作、复位路径、平台行为或作者意图。
- 不把变量命名、原注释、Skill 规则或通用 PLC 常识单独当作工程行为证据。平台/库语义缺少依据时标注假设或未知。
- 示例使用真实变量与连贯输入/状态轨迹，说明必要假设；不得把纸面推演表述为编译、仿真或实机结果。

### 4.1 讲解后的批判性审查

在程序逻辑讲解之后增加独立的“批判性审查”部分。审查对象是代码及其可见工程证据，不以讲解程序本身作为正确性证明；程序可能存在逻辑缺陷、边界遗漏、可维护性或可诊断性不足，也可能因资料不全而无法判断。

- 先区分“源码可直接证明的问题”“依赖平台语义/需求的风险”“资料不足、待确认的问题”；每项给出代码位置/工程证据、触发条件、可能影响和置信度。
- 按严重程度与证据强度排序。可检查：不可达或矛盾条件、分支顺序/覆盖、状态无法退出或错误复位、保持/清除不对称、多个写入者/执行顺序、计时器/边沿/扫描周期假设、越界/类型转换、故障与超时处理、输出安全状态、诊断事件是否可观察、接口/IO 映射是否未解析，以及嵌套逻辑可读性。
- 每个发现说明反例或反向推演：什么输入/状态组合会暴露该问题？若证据不足，不虚构后果，应明确待核实的设备手册、需求、任务配置、交叉引用或运行时记录。
- 将逻辑正确性、可维护性、可诊断性和安全影响分开表述。凡涉及人员/设备安全、失效安全或安全等级的结论，只指出可见证据与缺口，不作安全认证或“安全/不安全”的无依据结论。
- 对潜在问题提出验证建议（代码审查、边界用例、静态检查、编译、仿真/Trace、现场确认等），清楚标注哪些尚未执行。没有发现已证实缺陷时写“本次材料未发现可由现有证据确认的问题”，并列出审查范围和未覆盖风险，不宣称程序完美。
- 评估程序时不得擅自改写 PLC 源码或将建议当成用户批准的修改；如需修复，另行取得明确授权。

## 5. 代码分块与嵌套结构讲解

- 代码按逻辑边界拆成可读小块，避免一次展示过长代码；不得为缩短而漏掉请求范围内代码。
- 大型 `IF`、`CASE`、`FOR` 等外层闭合结构中若含多个内部逻辑子块：先交代外层完整范围、入口条件及整体作用；再按分支、状态更新或数据处理分批讲解；最后汇总完整执行顺序、分支关系、输入输出和状态变化。
- 每个子块须保留外层条件及必要上下文，说明条件、读取/写入、状态影响及与前后子块的关系。明确分支优先级/互斥关系，以及多个独立 `IF` 可能依次执行、后写覆盖前写等行为。
- 可使用源码行范围、锚点和局部上下文避免重复粘贴长源码；不得将子块讲成互不相关的程序，也不得暗示未执行的分支已执行。

## 6. 行内 AI 注释规范

- 在教学代码副本中，尽可能为每条非空代码行添加简洁、准确、符合该行真实作用的行内解释，包括条件、赋值、调用、分支控制和闭合行。
- 仅在确实无法安全注释、语言语法不允许或注释会破坏代码可读性的情况下例外；每个漏注例外应说明原因，不得静默漏注。
- 所有新增的 AI 行内讲解注释以固定英文标识 `AI:` 开头。原始源码注释原样保留且不加该标识；若需补充原注释含义，另加 `AI:` 注释，不能伪装为作者原注释。
- AI 注释只能写在教学副本，不得回写 PLC 工程源码。教学副本须能逐行对应原始代码，保留原始内容供核对；补充解释不得超出源码证据，不确定处标“未知”。

## 7. Skill 标准化与隐私

- 规范化基线采用 Anthropic Skills 格式，并验证其在 Codex Skills/`AGENTS.md` 加载体系中的兼容方式；不能把两套规范假定为相同，差异及无法兼容项须以官方文档和实测记录。
- 对 Skill 本体脱敏，尽量移除邮箱、姓名/作者标识、用户或本机可识别信息；保留功能、用途描述、触发条件和完成功能必需的 Skill 本体内容。
- 对平台必需字段、可选身份字段和 Skill 功能正文分别核对；先确认规范要求，再决定字段可省略、匿名化或保留，避免脱敏导致 Skill 不可用。
- 基于 Skill 生成的交付文件（如代码讲解文档、样稿、评估报告）不因本项目而统一脱敏，是否脱敏按用户对单份文件的要求处理。
- 需求文档与可分发 Skill 不点名作为规则参考的具体私有项目、仓库、路径或本机身份；从既有实践抽取通用规则时须去标识化。

## 8. Git 迭代、提交格式与隐私钩子

- 使用 Git 可追溯迭代，改动按小而聚焦的提交组织，利于审查、回滚和定位回归；提交仅记录代码/文档改动，不自动触发 Skill 版本号更新或发布。
- Skill 采用语义化版本；日常 Git 小提交不升版本号。验收后的版本发布节点才更新版本元数据/变更记录：向后兼容的功能或内容能力升级升 minor，文档/规则修正升 patch，破坏性架构或格式变更升 major。每次发布是否打 Git tag 按发布流程记录。
- 提交信息规则从已检索的既有实践抽象为通用格式，不在 Skill/需求正文中标出参考项目身份：`type(scope): 中文标题`；`type` 为受控英文小写类型，允许值固定为 `feat`、`fix`、`docs`、`refactor`、`chore`、`merge`、`perf`、`release`、`revert`、`test`、`build`、`ci`、`style`；`scope` 为英文小写；标题含中文且不超过 100 字符；标题后空行；正文至少一条 `- ` 分条。
- 提交格式与隐私钩子作为 Skill 仓库级文件纳入版本控制，并仅对该仓库生效；配置该仓库使用仓库钩子，不修改全局 Git 配置，也不要求安装全局钩子。现有宿主机级隐私保护不得因仓库配置而被无意绕过；实施方案需明确串接/委托边界并验证实际执行链。
- 隐私钩子检查提交新增内容及路径，覆盖疑似 API/访问令牌、硬编码凭据、私钥、非公开个人邮箱、真实 IP/绝对用户路径、凭据或签名文件、构建缓存和非项目个人素材。明确允许的公共 noreply/占位符规则须最小化并有测试。
- 钩子及日志不得回显密钥、令牌、邮箱、IP 等敏感值；只报告风险类别和必要的文件位置。钩子不得静默改写内容，不提供未经批准的旁路。
- 先检查 Git 实际生效的 hook 路径/委托关系，再验证实现；正反例测试之外，使用隔离临时 Git 仓库确认合法提交实际成功、违规提交实际被阻止。不得影响真实历史、绕过宿主机安全钩子或泄露测试数据。

## 9. 模板与文档可读性
