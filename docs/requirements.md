# PLC 程序学习 Skill 需求

## 1. 目标

面向不同品牌 PLC 工程及复杂程序框架，按证据梳理工程结构和程序关系，再让用户选择要学习的代码部分。Skill 按标准化流程分析所选代码，生成初学者能读懂、可复核的 Markdown 讲解手册，并引导用户逐步建立对局部逻辑和整体工程的理解。

## 2. 任务路由与优先级

- 根据用户的自然语言请求确定流程；默认用简短请求即可开始，不要求用户重复提供长清单。只有缺失资料会实质影响分析时才追问。
- 面对复杂工程时，先呈现有证据支持的结构、程序关系、可选讲解对象和资料缺口，再由用户选择下一步。用户已指定代码时直接进入分析；用户可随时跳转或提出具体问题，不被学习顺序限制。
- 简单事实问答直接回答；用户选择局部代码后，只分析所选范围及必要上下文；整体工程地图和完整手册按用户选择或任务需要展开。详细讲解完成后交付 Markdown 手册，并简要指出可继续学习的相关部分。
- 每项代码分析都满足 P0 核心要求；P1 仅在触发时执行；P2 按相关性选用；P3 仅用于 Skill 开发维护，不强加给普通讲解。
- 发生冲突或篇幅受限时，依次优先：用户本次目标、真实性与源码覆盖、执行因果和未知边界、已触发的条件要求、可选增强。不得为补充内容挤占核心解释。

| 层级 | 适用范围 |
|---|---|
| P0 核心 | 源码忠实、范围完整、因果清楚、证据边界明确、批判审查、验证诚实 |
| P1 条件 | 工程地图、品牌资料查证、安全影响、复杂轨迹、长文交付、解析能力声明 |
| P2 增强 | 系统思维、额外示例、边界反例、对照解释、可视化 |
| P3 治理 | Skill 架构、解析器、评测、Git 门禁、版本和发布 |

## 3. 工程识别与支持范围

- 先判断输入类型、可读范围、目标对象及版本线索。恢复工程树、声明、实例、调用和读写关系时，只陈述有文件或工具证据支持的内容；缺少证据就标为“未知”并指出缺口。
- 涉及厂商工程、I/O、事件、报警或 IDE 操作时，先确认品牌、产品线、格式和版本，再查对应官方资料。普通文本片段可直接分析，不要求先完成品牌适配。
- 首批关注西门子、欧姆龙、倍福和台达。解析能力按品牌、产品线、格式、版本分别验证；未验证前不得宣称支持。Skill 研发阶段的外部案例与资料调研，不属于普通代码分析流程。

## 4. 代码分析与审查

- 详细讲解覆盖用户请求范围内所有可读源码；需要呈现源码时完整保留该范围，不以摘要、关键片段或省略号替代。资料不完整时说明已覆盖与未覆盖部分。
- 解释相关条件与分支、执行顺序、变量读取和写入、未写入、结果及状态变化；说明代码块职责、解决的问题，以及已知的上下游关系。变量名、注释和通用习惯不能单独证明程序行为。
- 清楚区分源码事实、带前提的推演、推断和未知；不编造调用顺序、任务周期、设备动作、复位路径、平台语义或作者意图。
- 讲解后单列批判性审查，按证据区分源码可证问题、条件风险和资料缺口。发现应说明位置、触发条件、可能影响及置信边界；无可证实问题时说明审查范围，不宣称程序完美。安全相关内容只指出证据与缺口，不作安全认证。
- 如未运行编译、静态检查、仿真、Trace 或实机验证，明确标为未执行；格式检查通过不等于逻辑正确。

## 5. 代码分块

按完整逻辑边界展示，不得为缩短而漏代码。大型 `IF`、`CASE`、`FOR` 等结构先说明外层范围和入口，再解释内部子块，最后汇总执行顺序、分支、读写与状态关系；说明多个独立条件可能连续执行及后续写入覆盖前值的情况。

## 6. 行内 AI 注释

- 默认对每条非空源行（含条件续行与结构闭合行）在完整原行后追加简洁准确的 ` // AI: ` 尾注；空白、纯注释与未闭合块注释内部行除外。
- 每条尾注写对象与动作，并执行删除测试：无实际信息损失就改写，不用“执行赋值”“条件成立”一类空话占位。
- 保留原字符与作者注释，只在行末追加；同一行已有本轮尾注时不叠加。用户当次明确要求原样源码时不追加。
- `--legacy-selective` 只用于复核 2.x 历史夹具，不得用它放宽新稿门禁；任何情况下都不回写 PLC 工程源码。

## 7. Skill 规范与隐私

- 以 Anthropic Skills 规范为基线，并实际验证目标平台的 Skill/`AGENTS.md` 加载兼容性；不能仅凭格式相似宣称兼容。
- Skill 自有说明默认使用简体中文；源码、技术标识、API、命令、路径和平台必需字段保留原样。Skill 本体应去除不必要的个人身份和本机信息；生成给用户的交付物不默认统一脱敏。
- 指定的外部评测输入及其衍生内容留在仓库外，不写入 Skill、仓库或评测记录。评测不得泄露样本事实、专属规则或可识别细节。

## 8. Git 迭代、提交格式与隐私钩子

- Git 门禁只作用于本仓库，不修改全局配置，并须保留现有宿主隐私检查链。扫描报告不得回显敏感值；具体实现和验证范围见[维护规范](maintenance/governance.md)。
- 提交格式为 `type(scope): 中文标题`，使用已批准的类型集合；Git 日常小提交不自动升版，语义化版本只在获准发布时更新。
- 不擅自修改既有用户改动；提交、推送、合并、安装或发布均须取得对应授权。分支开发许可不自动包含这些操作。

## 9. 输出与验收

- 用户选定的详细讲解按标准模板组织：功能定位与执行条件、源码、代码块整体讲解、形象示例、程序交互与段间交接。关键变量表放在源码之前，列出变量、类型、方向、含义、读写者和证据等级；整体讲解说明处理过程、关键逻辑、写法好处和状态变化。完整手册写为独立 `.md` 文件并交付路径或链接；隔离评测产物留在仓库外，短事实问答不强套模板或强制生成文件。
- 示例使用真实变量和明确假设，足以复算关键路径；涉及边界、状态、多次写入或时序时，说明输入、前态、条件、写入/未写和结果。没有时间证据时不虚构扫描周期。
- 长篇手册按完整逻辑单元分段，最终合并并交付一份完整 Markdown；短答不强制生成文件。
- 验收以真实产物为准，分别检查源码覆盖与保真、因果推理、可读性、注释价值、未知边界、批判审查、隐私和实际验证。盲测使用常规简短请求，生成与评审隔离；不得把详细评分提示提供给生成会话。

## 10. 开发边界

Skill 改造按“需求确认、现状审计、方案设计、分步实现、独立验证、用户验收”推进。需求定义目标，实施计划记录任务与证据；不得将普通代码分析规则扩展为开发治理步骤。保护现有工作区改动，不修改作为输入的 PLC 工程源码。当前进度、已完成项和未验证项以[实施计划](plans/2026-11-08-plc-skill-requirements-alignment.md)及[追溯表](architecture/traceability.md)为准。
