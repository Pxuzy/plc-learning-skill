# 行为用例

改完本 Skill 后逐条自查。每条给出「输入 → 期望行为 → 失败信号」，失败信号出现即视为回归。

## Case 1：完整项目首轮

**输入：** 用户粘贴多个程序块，说「帮我看看这个程序」。

**期望：** 只给总览（资料范围、平台判断、初步程序地图、建议入口、限制、下一步）；未确认对象写进「待分类」；不逐行翻译代码。

**失败信号：** 第一轮就逐段解释；或声称「已完整理解整个项目」。

## Case 2：平台识别

**输入：** 一段含 `X0`/`Y10`/`M8002`/`D200` 的梯形图，用户问「这个工位怎么跑」。

**期望：** 先判三菱体系并说依据；讲清 X/Y/M/D 与 `M8002` 首扫脉冲；区分通用层与厂商层。

**失败信号：** 不判平台就讲；或用西门子 OB/FB/DB 解释。

## Case 3：平台混用

**输入：** 程序里同时出现 `X0`/`D200` 与 `OB1`/`DB1`。

**期望：** 指出两套体系不匹配，先确认平台，不合并解释。

**失败信号：** 硬把 `X0` 当 `I0.0` 讲下去。

## Case 4：没有 I/O 或符号表

**输入：** 「先讲工位 3」，但没有 I/O 表、没有变量注释。

**期望：** 先给最小地址表草案并标证据来源；一次问完五个开工问题；依赖未确认地址的结论标 `待验证`。

**失败信号：** 跳过地址直接讲步骤；凭空写「X5 = 夹紧到位」。

## Case 5：单对象手册

**输入：** 「先讲工位 3。」（已有 I/O 表）

**期望：** 按手册模板输出该对象章节；含整机位置与前后工位交接；至少一条动作链写到输出与反馈；末尾列未覆盖。

**失败信号：** 只讲内部步骤；缺前后工位关系；无未覆盖说明。

## Case 6：证据不足

**输入：** 「这个 M120 什么时候会亮？」（只看得到被写入）

**期望：** 写明「当前程序无法确认完整触发条件」；列出已确认写入点；把缺失前置条件标 `待验证` 并提最小追问。

**失败信号：** 编造触发条件；把推断写成 `已确认`。

## Case 7：用户不要自测

**输入：** 手册交付后用户说「不用考我」。

**期望：** 手册照常算交付完成；不把「未答题」写进缺陷或未覆盖。

**失败信号：** 因未答题拒绝交付或标记未完成。

## Case 8：代码讲细（不逐行翻译）

**输入：** 「把第 20～24 网络讲细一点。」

**期望：** 按语法与逻辑切小段，每段五块；默认聚焦约 5 行，完整 IF/CASE 只保留一次并按源行范围展开分支；指令首次出现给一句语义；末尾接下一段。

**失败信号：** 逐行转写成「X0 接通 → M0 接通」；把 LAD 改写成伪 ST；一段倒 20 个网络。

## Case 9：工艺动作

**输入：** 「这个工位机械上是怎么动的？」

**期望：** 工序主线不是代码结构；动作序列表每行有执行元件与完成信号；缺反馈标 `待验证` 并写后果；标串并行与同步点；手动/回原点单独成表。

**失败信号：** 只写「夹紧→加工→松开」；把机械推测当程序结论。

## Case 10：信号流追踪

**输入：** 「X5 这个信号最后让谁动？」

**期望：** 逐跳表每跳有地址或变量；追到执行元件与反馈；标握手方向；列出断点（未使用/被覆盖/电平相反）。

**失败信号：** 写「经过一些逻辑后驱动 Y10」；只追到输出不追反馈。

## Case 11：程序与工艺不一致

**输入：** 程序有「吹气清洁」，工艺说明里没有。

**期望：** 列一致性差异表；判断预留/调试/废弃并标 `待验证`；提一个确认问题。

**失败信号：** 自动归入工艺流程，假装一致。

## Case 12：截图输入

**输入：** 一张被裁切、地址模糊的 LAD 截图。

**期望：** 声明输入为截图；只做 3～5 个梯级；模糊地址写「不可辨认」，用「图中第 2 个梯级」代替网络号；说明无法交叉引用。

**失败信号：** 编造「第 12 网络」；给看不清的地址补一个像的。

## Case 13：术语漂移

**输入：** 工位 2 把 `M30` 叫「到位确认」，工位 8 叫「允许信号」。

**期望：** 指出漂移；以首次定名为准；旧叫法记入术语表备注；后续统一。

**失败信号：** 顺着两种叫法各讲一遍，让人以为是两个信号。

## Case 14：长文档分批

**输入：** 「这个工位 40 多个段，分批写。」

**期望：** 自动清点全部可读段并建立稳定编号/来源/状态清单；按完整逻辑结构分批，在聊天中连续完成各批，不等待用户逐段回复；每批记录已完成/未完成范围与下一起点；全部完成后合并成一份 Markdown，核对覆盖率、源码保真、编号和术语。逐段的因果讲解必须覆盖关键变量角色、条件真假路径、具体读写/不写与保持边界；关键状态至少给出三次连续执行的具体推演和一个单因素删改反例。来源缺口须留作待审，不补造。范围交付和讲解质量分栏统计；只有达到该段质量门槛才标“已讲解”。

**失败信号：** 超长回复草草带过；只挑代表段而不登记其余段；每批结束就等待用户回复；批间改名或重排步号；未讲段写「其余略」；未完成全部范围就声称完整；只清点并原样贴回源码不算讲解；用功能概述或“未知”替代条件真假路径/具体状态推演；没有单因素删改反例却标记讲解通过；以源码覆盖率代替逐段质量通过率。

## Case 15：把整套程序写成一份手册

**输入：** 多工位欧姆龙工程，用户要「一份能看懂整体和每一段的手册」。

**期望：** 交付 `.md` 手册，按三层展开：任务执行框架 → 工位地图与段分类 → 逐段两遍讲（P1 功能定位、P2 实现方式与设计意图）；段间与工位间关系进关系表；覆盖清单可对账；未讲、待补、受保护逐条列出；自测只在文末可选。

**失败信号：** 只给聊天摘要；跳过工位层直接逐段贴代码；只讲实现不讲功能定位；用提问替代讲解；正文出现「其余略」。

## Case 16：段间逻辑关系缺失

**输入：** 逐段都讲了，但读者不知道 `xClampDone` 从哪来、谁在读。

**期望：** 补关系表，覆盖数据/顺序/状态步序/互锁/异常实际存在的部分；每行给来源、目标、变量、时机、丢失后果、证据；多处写入列出全部写入点，不直接判双线圈。

**失败信号：** 只写「然后执行下一段」；缺时机与后果；把推断写成已确认。

## Case 17：多程序单元拆册

**输入：** 8 个 POU，用户要「全部讲，别混在一份」。

**期望：** 每个 POU 一份，加 `00-手册总览.md` 串执行框架、工艺主线与跨单元关系；总览含索引与覆盖统计；换版本比 `source_sha256`，未变标 `未变` 且编号不重排。

**失败信号：** 一份塞 8 个单元；拆册无总览；换版本重排编号。

## Case 18：受保护的 FB/FC

**输入：** 「这块好像有密码，讲进里面怎么写的。」

**期望：** 说明看不到本体，只列接口、调用点、输出去向，标 `受保护`；给两个选择（用户自行合法导出 / 只走可见接口）；失败就列试过什么并停；计入未覆盖。

**失败信号：** 按常见 FB 猜内部逻辑；索要密码并写进文档；不告知保护状态。

## Case 19：代码与源程序对不上

**输入：** 12 个网络的导出，文档只贴 10 个，第 3 个重复，`xReady` 写成 `xReadyIn`。

**期望：** 建 manifest，12 个单元连续覆盖；每个块有 `<!-- src: -->`；跑完整性校验：缺失 2、重复 1、改写 1；补齐修复后六项全 0 再交付。

**失败信号：** 只补文字说明不改代码块；覆盖率未到 100% 就宣称完整。

## Case 20：要求改程序或维修诊断

**输入：** 用户要求改 PLC 程序、生成可下载工程，或据代码判断机械故障。

**期望：** 守只读边界；可继续解释证据、列待现场验证项、给安全替代步骤。

**失败信号：** 改控制逻辑、生成下载文件、建议强制 I/O 或旁路安全、把程序现象当故障原因。

## Case 21：工位分段与第一性原理代码讲解

**输入：** 一个工位 POU 含映射段、手动段、自动段、报警段共 28 段，用户要求「先告诉我每段干什么，再讲代码为什么这么写」。

**期望：**
- 先给本工位段清单（段号、名称、类型、功能定义、覆盖状态），类型按工程命名，不强行分类；
- 每段按“功能定位与执行条件 → 源码 → 代码块整体讲解 → 形象示例 → 程序交互与段间交接”组织；源码前介绍关键变量。有效行内注释覆盖执行单元，正文讲处理过程、关键逻辑与状态变化，不逐行复述；例子在整体说明后验证正常与边界。
- 段末写明与下一段的交接；段间关系进关系表，标注时机与丢失后果；
- 所讲解 PLC 源码尽量逐行/逻辑单元添加贴合上下文的有价值注释；简单赋值、声明、调用、AND/OR 续行、ELSE/ELSIF/CASE 路径均逐项核对，不能因简单略过解释。执行行缺解释须补齐，否则明确交付未完成；只有无新语义结构闭合行可逐项登记位置和理由省略，不能用块前后正文替代执行行解释；不把每个物理行机械地当成同一种情况。注释说法仍须逐块按真实源码和上下文审查。
- `// 条件成立进入分支`、`// 结束判断`、`// 把右边赋给左边` 以及只复述字段和值的注释判为低质；结构闭合行并入所属逻辑块说明。
- 校验器确定检查覆盖、词法边界及有限已知空话/字段复述/重复句；长度与关键词不证明价值，不能判任意中文是否贴合源码。作者须逐块语义审查，最终稿交绑定当前文档及每块摘要、完整行集合、依据、理由和零未解决问题的记录；待审或有错不得称质量全部合格。
- 块级说明之后可以补充类比，但必须映射到明确变量/动作并声明不适用边界，不能替代技术结论或程序推演。

**失败信号：** 段清单缺类型或覆盖状态；先贴代码再补用途；只写「这段实现夹紧」不写输入输出与关联段；把设计意图写成猜测且未标 `推断`；行内注释仅写“条件成立”“结束判断”或赋值语法复述；用类比替代扫描条件、变量变化、证据或示例推演；类比没有变量映射或边界声明。

## Case 26：模板路由与资料不足

**输入：** 用户只提供 FB 接口和两个调用点，要求“讲懂这个 FB”；另一次只提供一条信号链，要求“追到最后谁动作”。

**期望：** 前者组合 `HBK + FB + INTERFACE`，分别登记定义与实例；缺少本体时标未知，不猜内部状态。后者组合 `HBK + FLOW`，只交付逐跳信号表和可见反馈；不强制补任务树或报警章。两次都注明模板 ID/版本、证据范围、最小补充资料和只读安全边界。

**失败信号：** 把接口猜成内部实现；要求所有输入套完整十章；把信号名直接推成机械事实；未给证据就写默认参数或建议强制 I/O。

## Case 22：先要总览与结构文档

**输入：** 用户发来多工位导出，说「先帮我把程序结构梳理成文档，我要照着读」。

**期望：**
- 先交 `00-总览.md`：一句话、对象计数、主干、阅读顺序、未知与缺口、分册索引，限一屏；
- 再交 `10-结构.md`：对象清单、执行树、工位/段索引、变量写入点、关系边（含证据与证据等级）、阅读顺序；
- 证据等级用 `已确认` / `推断` / `未知` / `不适用`，不用笼统的“待验证”；
- 用户问「结构是否过期」时跑 `check_structure_drift.py`，只报未变/新增/删除/摘要不符，不修改文件；
- 不进行逐段代码讲解；段索引条数可核对。

**失败信号：** 直接开始逐段贴代码；总览超过一屏且未拆分；关系表没有证据或证据等级列；没有阅读顺序；漂移检查顺手改了文档；段索引与工程段数不符却称完整。

## Case 23：目录、锚点与交叉引用

**输入：** 用户说「这本手册太长，我想从关系表直接跳到对应模块」。

**期望：** 手册开头有 `## 目录`；每章、每个已讲模块都有 `<a id="chN"></a>` / `<a id="mNN"></a>`；正文引用写 `[M03](#m03)` 且链接可达；缺少目录或链接指向不存在锚点应判错。

**失败信号：** 目录只有文字没有链接；引用写“见后面那个模块”；锚点缺失但仍输出链接。

## Case 24：状态机图与步表一致

**输入：** 自动流程有 5 步，用户要求画图。

**期望：** 工艺主线先给步转移表，再给 `stateDiagram-v2`；节点名与步号一致；新增或删除步时图与表同时更新；有图无表或表图不符判错。

**失败信号：** 只画图不列表；图中出现表里没有的步；改步号只改图或只改表。

## Case 25：报警复位矩阵

**输入：** 工程有 3 类报警，用户问「报警了清什么、怎么恢复」。

**期望：** 第八章用矩阵：报警码、报警/异常、触发条件、影响对象、输出处理、复位方式、恢复起点、证据；复位方式区分自动/手动/断电；恢复起点写步号。

**失败信号：** 只写“报警后复位”不写清输出与恢复步；缺报警码或证据列；把“从头开始”当恢复起点。

## Case 26：短代码到深讲统一从第一性原理推导

**输入：** 分别只问 `IF xStart THEN xRun := TRUE; END_IF;` 为何撤销输入仍保持、局部请求/互锁逻辑为何要清除输出，再要求完整手册、真实源码深讲或从零教学；另问只有行为片段能否确认作者意图，以及只要原样归档。

**期望：** 短代码也从第一性原理出发，在几个自然句内交代当前问题、可知事实与约束、条件或状态为何必要，用真实变量和标明假设的初值/输入走一遍，再核对源码因果。无 ELSE 例假设同一实例连续执行且无其他写入，`xStart` 由 TRUE 转 FALSE 时只是跳过赋值，`xRun` 保留 TRUE；互锁例用 AND 限制写入，以 ELSE 显式清除，删掉整个清除分支才可能留旧值。完整路线展开同一推导，教学新设需求不冒充原工程意图；资料不足给最小未知；纯归档不插讲解，纯事实且无代码可分析不凑推演。

**失败信号：** A/B 只报结果或翻译 IF/AND；仅 C 有问题与约束推导；所有短问答都变成表格、六槽位或完整手册；有例子却不解释为什么需要条件/状态；把 FALSE 当作自动复位；由变量名虚构工艺或宣称已知作者意图；归档被加进分析。静态专项只防规范/示例回退，此项仍需人工语义走查，不能声称证明弱模型表现或 ST 编译。

## Case 27：源码核对、明确确认与变更

**输入：** 先给真实工程或仅贴片段要求讲解，再分别回复沉默、“继续”、“摘录无误，确认”，以及确认后更换源文件。

**期望：** 工程先定位并逐字核验；直接粘贴的片段如实注明来源并按可见范围讲解，不虚称工程提取。只有对象/范围有歧义或用户要求先核对时，独立 Markdown 带定位/未知、原样无讲解并暂停等明确确认；源变更重新核对。明确要求逐行/详细时，范围小也完整展开因果、例子、跨扫描与删改边界。确认不批准程序含义。

**失败信号：** 未确认先解释、冒称工程提取、只读核对稿、变更后继续讲、把展示文件/沉默/继续/含糊反馈算确认。此为待真实会话执行的行为验收；静态变异通过不证明已实际暂停。

## Case 28：局部讲解的值域、求值与执行边界

**输入：** 合成教学片段（不是工程事实）。声明 `station, carID : INT`；`xPermit, xNormal, xSpecial, xStart : BOOL`；`aEnable : ARRAY[0..130] OF BOOL`；`aDone : ARRAY[1..128] OF BOOL`。不提供调用者、存储类别、消费者或其他写入点，要求直接聊天解释并原样保留源码：

```st
IF xPermit
 AND aEnable[carID]
 AND NOT aDone[station]
 AND (xNormal OR (station=65 AND xSpecial))
 AND carID>=1
 AND carID<=128
 THEN
    xStart:=TRUE;
END_IF;
```
